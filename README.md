# law-rag

법제처 국가법령정보 OPEN API(DRF)로 법령을 수집해, **PostgreSQL + pgvector 하나로**
하이브리드 검색과 조문 인용 위법성 점검을 수행하는 CLI. 별도 벡터DB를 쓰지 않는다.

```
$ python -m lawrag.cli check "감사인이 회사의 재무제표를 대신 작성해 주었다"
```
문장을 넣으면 저촉되는 조문을 찾아 **법령명 · 조번호 · 시행일과 함께** 위법 여부를 판단한다.

---

## 구조

```
적재 ─ DRF API ──► parser ──────► embedder ──► PostgreSQL + pgvector
       (XML)      조 단위 청킹     model2vec     ├─ GIN  (bigram tsvector)
                  900자↑는 항                    ├─ HNSW (vector 256)
                  경계에서만 분할                  └─ token_df (문서빈도)

검색 ─ 질의 ──► 용어 확장 ──┬──► 임베딩 ────────► HNSW  ──┐
                (terms.yaml) │                            │
                             ├──► bigram ─────────► GIN ──┼─► RRF(k=60) ──► claude CLI
                             │    └ df>10% 토큰 제거      │        │
                             └──► 덧붙인 법령용어 ──────────┘   판정 + 조문 인용
                                  └ term_article (용어→조문 연계)
```

| 단계 | 파일 |
|---|---|
| 수집 | `lawrag/drf_client.py` |
| 파싱·청킹·토큰화 | `lawrag/parser.py` |
| 임베딩 | `lawrag/embedder.py` |
| 질의 확장 (일상용어→법령용어) | `lawrag/terms.py`, `lawrag/terms.yaml` |
| 용어→조문 연계 (검색 3번째 축) | `lawrag/drf_client.py`, `sql/schema.sql: term_article` |
| 적재·하이브리드 검색 | `lawrag/db.py`, `sql/schema.sql` |
| 위법 판단 | `lawrag/judge.py` |
| CLI | `lawrag/cli.py` |

## 설계 결정

| 결정 | 근거 |
|---|---|
| 청크 = **조(條) 단위**, 900자 초과 시 **항 경계에서만** 분할 | 고정 길이로 자르면 "제8조 제2항"이 두 청크로 갈려 **인용이 불가능**해진다. 항 하나가 통째로 900자를 넘어도 쪼개지 않는다 |
| 임베딩 텍스트 앞에 `법령명 제N조(제목)` 헤더 prepend | 청크 단독으로는 지시대명사 문장의 의미가 소실된다 |
| 벡터 + 키워드 + **용어연계 3축 하이브리드**, RRF(k=60), 가중치 전부 1.0 | 벡터는 조번호 같은 정확 식별자에 약하다. 두 점수는 스케일이 달라 가중합이 불안정하므로 순위만 쓰는 RRF. 가중치를 주면 지표가 오르는 조합이 있으나 전부 회귀를 동반해 도입하지 않았다 |
| **법령용어→조문 연계를 세 번째 축으로** (`term_article`, DRF `lstrmRltJo`) | `사업연도` 는 청크의 40%에 나와 키워드 축이 통째로 무력하다. "이 용어를 규율하는 조문" 이라는 **법제처가 매긴 외부 신호**는 벡터·키워드 어느 쪽으로도 복원되지 않는다 |
| 한국어 키워드 = **Python bigram → `to_tsvector('simple')`** | PostgreSQL 기본 FTS는 한국어를 공백 단위로만 끊는다. mecab-ko 설치 의존성을 피했다. 단어 원형도 함께 넣어 `제3조` 같은 식별자를 정확히 잡는다 |
| 질의 토큰 중 **문서빈도 10% 초과는 버림** (`token_df`) | bigram `법인` 은 청크의 93%에 나온다. 안 거르면 `ts_rank_cd` 가 노이즈 밀도로 순위를 매겨 **하이브리드가 벡터 단독보다 나빠진다** (아래 측정) |
| **일상용어→법령용어 사전으로 질의 확장** (임베딩하지 않음) | 법이 용어를 바꾸면(접대비→기업업무추진비) 일상어가 코퍼스에 0건이라 검색 자체가 불가능하다 |
| 조문 본문 **SHA256** 저장 | 개정 시 변경된 조문만 재임베딩 (`refresh`) |
| `조문여부='전문'` 제외 | 이 값은 조문이 아니라 장 제목("제1장 총칙")이다. 법인세법 기준 255개 중 42개가 여기 해당하며, 안 거르면 알맹이 없는 청크가 16% 섞인다 |
| 벡터DB 미사용 | 목표 규모 ~2천 청크. HNSW로 충분하고 메타데이터 필터를 같은 SQL에서 처리한다 |

## 코퍼스

**법인세 + 외부감사 2축으로 의도적으로 좁혔다.** (`lawrag/cli.py: TARGET_LAWS`)

- 법인세법 / 법인세법 시행령
- 주식회사 등의 외부감사에 관한 법률 / 동 시행령

국세청 해석 16만건·심판례 52만건 전체를 긁지 않는다.

## 설치

```bash
python3 -m venv .venv && .venv/bin/pip install -e .
cp .env.example .env      # LAW_OC 에 신청 이메일의 @ 앞부분을 넣는다
```

PostgreSQL 17 + pgvector 가 필요하다. `docker-compose.yml` 로 띄우거나,
macOS 라면 [Postgres.app](https://postgresapp.com) 이 pgvector 를 번들한다.
Docker 를 쓸 수 없는 환경에서는 conda-forge 로 sudo 없이 설치할 수 있다
(이 프로젝트의 개발 환경이 그랬다):

```bash
micromamba create -p ./pgenv -c conda-forge postgresql=17 pgvector
./pgenv/bin/initdb -D ./pgdata -U lawrag
./pgenv/bin/pg_ctl -D ./pgdata -o "-p 5433 -k /tmp" -l ./pgdata/server.log start
```

```bash
python -m lawrag.cli init-db
python -m lawrag.cli ingest
python -m lawrag.cli refresh-terms   # 용어→조문 연계 (검색 3번째 축). 몇 분 걸린다
```

## 사용

```bash
python -m lawrag.cli search "감사인 독립성"     # 세 축의 순위를 함께 표시 (v#/k#/t#)
python -m lawrag.cli check "<점검할 문장>"      # 위법 여부 + 근거 조문
python -m lawrag.cli eval                      # Recall@5 / Recall@10 / MRR
python -m lawrag.cli refresh                   # 개정된 조문만 재임베딩
python -m lawrag.cli refresh-terms             # terms.yaml 을 고쳤을 때만
```

## 검색 품질

`eval/questions.yaml` **30문항**(법인세 20 + 외부감사 10), 코퍼스 1,127청크 기준.

```
Recall@5 0.867    Recall@10 0.933    MRR 0.657
```

질의는 조문 제목을 베끼지 않고 사람이 물어볼 법한 구어체로 썼다 —
조문 제목을 그대로 쓰면 키워드 검색이 거저 맞혀서 지표가 부풀려진다.
문항을 늘릴 때는 **정답 조문을 검색 성능과 무관하게 먼저 고르고, 질문을 다 쓴 뒤에야
평가를 돌린다.** 검색해 보고 잘 맞는 질문만 남기면 지표는 오르지만 아무 의미가 없다.
정답이 본법·시행령 양쪽에 걸리는 주제는 아예 뺐다(정답이 하나로 확정되지 않는다).

### 어떻게 여기까지 왔는가

아래는 **15문항 시절의 측정 이력**이다. 위 30문항 숫자와 분모가 다르니 섞어 읽으면 안 된다
(같은 코드로 15문항을 재면 MRR 0.684 가 나온다). 개선 판단은 **같은 문항 집합 안에서**만 했다.

| 방식 | Recall@5 | Recall@10 | MRR |
|---|---|---|---|
| 벡터 단독 | 0.667 | 0.667 | 0.483 |
| 키워드 단독 | 0.333 | 0.467 | 0.243 |
| 하이브리드 RRF | 0.533 | 0.667 | 0.466 |
| + 문서빈도 필터 | 0.667 | 0.733 | 0.536 |
| + 용어 사전 질의 확장 | 0.800 | 0.867 | 0.668 |
| + 용어연계 조문 축 (3축) | 0.800 | 0.933 | 0.675 |
| **+ 축3 안에서 용어 등장 횟수 tie-break** | **0.867** | **0.933** | **0.684** |

### 하이브리드가 처음엔 벡터 단독보다 나빴다

측정해 보니 하이브리드(0.533)가 벡터 단독(0.667)보다 **낮았다.** 원인은 임베딩이 아니라
한국어 bigram 토큰화에 있었다. `법인세율은` 을 bigram 으로 쪼개면 `법인`·`인세` 가 나오는데,
이 조각들은 코퍼스의 **93% / 88%** 청크에 등장한다. 정작 변별력 있는 `세율` 은 3% 다.
이걸 전부 OR 로 묶으면 `ts_rank_cd` 가 사실상 노이즈 밀도로 순위를 매긴다.

그래서 질의 토큰 중 **문서빈도가 청크의 10% 를 넘는 것을 버린다**(`db.MAX_DF_RATIO`).
문서빈도는 `ts_stat` 으로 집계해 `token_df` 테이블에 두고 ingest 때마다 갱신한다.
0.5~0.1 구간이 모두 비슷하게 좋은 넓은 평탄역이라 문항 수에 과적합된 값은 아니다.

이 필터를 넣고 나서야 **하이브리드가 두 축 단독보다 모두 나아졌다**(MRR 0.536 > 벡터 0.483).
`법인세율은 몇 퍼센트인가요` 는 순위권 밖 → 3위, `법인세를 연중에 미리 나눠 내야 하는 의무` 는
10위 → 3위로 올랐다.

### 그다음 실패 4건은 전부 용어 격차였다

`접대비` 는 코퍼스에 **0청크**다. 법이 용어를 `기업업무추진비`(19청크)로 개정했기 때문이다.
검색을 아무리 튜닝해도 없는 단어는 찾을 수 없다. 정적 임베딩도 이 도약을 못 한다.

그래서 `lawrag/terms.yaml` 에 일상용어 → 법령용어 사전을 두고 질의에 법령용어를 덧붙인다.
**이 사전은 임베딩하지 않는다** — 질의 전처리에서 조회만 한다.
확장문은 벡터·키워드 **양쪽**에 쓴다 (한쪽에만 쓰면 이득이 절반: R@5 0.733 vs 0.800).

| 질의 | 기대 조문 | 격차 (코퍼스 등장 청크 수) | 결과 |
|---|---|---|---|
| 접대비를 한도보다 많이 썼는데 | 법인세법 제25조 | 접대비(0) → **기업업무추진비**(19) | MISS → **1위** |
| 감사보고서에 거짓을 적으면 처벌 | 외부감사법 제39조 | 처벌(1) → **벌칙**(6)·징역(10)·벌금(13) | MISS → **1위** |
| 지난해 적자를 올해 소득에서 빼려면 | 법인세법 제13조 | 적자(1) → **결손금**(77) | 여전히 MISS |
| 회사의 회계기간은 어떻게 정하나요 | 법인세법 제6조 | 회계기간(6) → **사업연도**(449) | 여전히 MISS |

사전 항목은 추측이 아니라 위 등장 횟수를 세어 보고 넣었다. 새 항목도 같은 방식으로 확인할 것.

### 남은 2건은 "용어가 너무 흔해서" 못 찾은 것이었다

`사업연도` 는 청크의 **40%(449)** 에 나온다. 질의 확장이 이 말을 덧붙여 줘도 문서빈도
필터가 도로 걸러내므로 키워드 축이 통째로 무력하다. **흔한 법령용어로는 조문을 특정할 수 없다.**

빠져 있던 건 "이 용어를 규율하는 조문이 어느 것인가" 라는 정보다. 코퍼스 안에는 없지만
법제처가 `lstrmRltJo`(법령용어→조문 연계) 로 이미 매겨 놓았다. 이걸 **세 번째 검색 축**으로
넣었다 — 핵심용어(용어를 정의·규율하는 조문) 먼저, 같은 핵심용어끼리는 **그 용어가 조문에
많이 나오는 순**, 그 안에서 벡터 거리순.

| 질의 | 벡터 축 | 키워드 축 | 용어연계 축 | 최종 |
|---|---|---|---|---|
| 회사의 회계기간은 (제6조) | 14위 | **못 찾음** | **2위** | MISS → **4위** |
| 지난해 적자를 (제13조) | 24위 | **못 찾음** | 7위 | 여전히 MISS |

**축 단독 성능이 곧 융합 결과는 아니다.** RRF 는 한 축에만 잡힌 문서를 크게 올리지 못한다 —
축3 2위(`1/62`)는 다른 청크의 벡터 1위(`1/61`) 하나에도 밀린다. 그래서 축3 이 2위로 잡은
제6조가 처음엔 최종 9위였다. 가중치를 주면 올릴 수 있지만, 그렇게 만든 조합은 **전부**
다른 문항을 회귀시키거나 평탄역이 없어 채택하지 않았다.

대신 **축3 안쪽 순서**를 고쳐서 올렸다. `사업연도` 의 핵심용어 조문은 여럿인데 그중 어느
것이 제6조인지 가릴 신호가 없었다. 조문 본문에 그 용어가 몇 번 나오는지를 두 번째 정렬 키로
넣자 제6조가 핵심용어 조문 중 1위가 되고, 최종 9위 → **4위**가 된다(R@5 0.800 → 0.867).
가중치가 아니라 tie-break 라 **튜닝할 값이 없다** — `ln(1+x)` 를 씌워도 결과가 완전히 같고,
축3 이 발화하지 않는 질의에서는 RRF 점수가 소수점 12자리까지 기존과 동일하다.
다만 15문항 중 움직인 건 이 1문항뿐이라, 회귀가 없다는 것 이상의 강한 증거는 아니다.

`joRltLstrm`(조문→법령용어, 역방향)도 조사해 이 아이디어를 얻었지만, API 가 세는 값
(연계 지점)과 본문에서 센 횟수는 서로 다른 신호였고 **지표는 같았다.** 같은 결과라면
조문당 1회씩 부르는 수집 경로가 필요 없는 쪽이 낫다고 보고 본문 쪽을 썼다.

남은 제13조는 결손금의 **핵심용어가 아니라 선정용어**다 — 제13조(과세표준)는 결손금을
정의하는 조문이 아니라 공제 절차를 규정하는 조문이라 법제처가 그렇게 분류했다.
정렬을 뒤집으면 이 문항은 고쳐지지만 제6조가 도로 깨진다.

## 알려진 한계

- **`ts_rank_cd` 는 BM25 가 아니다.** 진짜 BM25 가 필요하면 ParadeDB `pg_search` 또는
  TigerData `pg_textsearch` 로 교체할 수 있다 (스키마 변경 불필요).
- **리랭커 미적용.** bge-reranker-v2-m3 등을 붙이면 정확도가 올라가지만 넣지 않았다.
- **임베딩이 정적(model2vec)이다.** 개발 머신이 Python 3.14 뿐이라 torch 휠이 없어
  BGE-M3 를 쓸 수 없었다. 정적 임베딩은 문맥을 반영하지 못해 문맥 의존 질의에 약하다.
  키워드 축과의 RRF 융합이 이를 부분적으로 보완한다.
- **용어 사전이 손으로 만든 소규모다.** `lawrag/terms.yaml` 은 실제 실패 문항에서 관찰된
  격차만 담고 있다(7항목). 평가를 30문항으로 늘리자 남은 실패가 **전부 이 격차**로 나왔다 —
  `계열사`→`특수관계인`, `모회사/자회사`→`지배회사/종속회사` 를 사전이 몰라서 놓친다. 법제처 「지능형 법령정보지식베이스」의 일상용어–법령용어 연계
  (`dlytrmRlt`)로 자동 확장할 수 있고 `target` 코드도 확인해 뒀지만, 아직 적용하지 않았다.
  **이 사전 크기가 곧 용어연계 축의 도달 범위다** — 사전에 없는 말이 들어오면 3번째 축은
  아예 발화하지 않고 검색은 기존 2축으로 돌아간다.
- **심판례·행정규칙·부처별 해석 미수집.** 조세심판원·증선위·국세청 해석의 `target` 코드값을
  공식 가이드에서 확인하지 못했다. 추정해서 넣으면 조용히 빈 결과를 적재하게 되므로 보류했다.
- **국세청·재정경제부 법령해석은 본문 API 가 없다.** 목록(안건명·링크)만 제공된다.
  웹 크롤링으로 우회하지 않고 이 한계를 명시하는 쪽을 택했다. 이런 자료는 스키마상
  `chunk.source_type='reference'` 로 구분되며 프롬프트에서 "본문 미제공"으로 취급된다.
- **회계감사기준·K-IFRS 는 법령이 아니라 이 API 에 없다.**
- **LLM 백엔드가 `claude` CLI 서브프로세스다.** API 키 없이 동작하지만 CLI 설치에 의존한다.
- **법률 자문이 아니다.** `check` 결과는 참고용이며 원문과 전문가 검토가 필요하다.
