# law-rag 작업 인수인계 브리프



---

## 0. 프로젝트 한 줄 정의

법제처 국가법령정보 OPEN API로 법령·행정규칙·심판례를 수집해,
**PostgreSQL + pgvector 하나로 하이브리드 검색 + 출처 인용 RAG**를 구현하는 CLI 도구.
별도 벡터DB 없음.잘구현되는지 검증 후 GitHub 공개 포트폴리오가 목표.

## 1. 현재 상태

### 완료된 것
- 레포 뼈대 작성 완료 (아래 구조)
- 파이썬 문법 검증 완료, bigram 토큰화 로직 단독 동작 확인
- 법제처 OPEN API 신청 **승인 완료**
- `lawSearch.do?target=law&query=법인세법&type=XML` 정상 응답 확인
  → `resultCode=00`, `totalCnt=3` (법인세법 / 시행령 / 시행규칙)
  → 응답 필드명이 `parser.py` / `drf_client.py` 기대값과 일치함을 육안 확인

### 아직 안 된 것
- `init-db` / `ingest` **미실행** (실제 DB 적재 검증 전)
- 심판례·증선위·부처별 해석 수집 미구현 (`target=law` 만 지원)
- 평가 스크립트 없음
- 용어 사전 기반 질의 확장 미구현

### 레포 구조

## 2. 확정된 설계 결정 (변경 시 반드시 근거를 물을 것)

| 결정 | 근거 |
|---|---|
| 청크 = **조(條) 단위**, 900자 초과 시 항→호 분할 | 고정 길이 분할하면 "제8조 제2항"이 갈려 **인용이 불가능**해짐 |
| 임베딩 텍스트 앞에 `법령명 제N조(제목)` 헤더 prepend | 청크 단독으로는 지시대명사 문장의 의미가 소실됨 |
| 벡터 + 키워드 **하이브리드**, RRF(k=60) 융합 | 벡터는 조번호 등 정확 식별자에 약함. 점수 스케일이 달라 가중합은 불안정 → 순위만 쓰는 RRF |
| 한국어 키워드 검색 = **Python bigram → `to_tsvector('simple')`** | PostgreSQL 기본 FTS는 한국어를 공백 단위로만 분리. mecab-ko 설치 의존성을 피하기 위한 선택 |
| 조문 본문 **SHA256 해시** 저장 | 법 개정 시 변경된 조문만 재임베딩 |
| 임베딩 = **BGE-M3(1024차원, 로컬, MIT)** | 무료·한국어 성능·상업적 이용 자유 |
| 벡터DB 미사용 | 목표 규모 ~1만 청크. pgvector HNSW로 충분하고 메타데이터 필터를 SQL로 동시 처리 가능 |

### 알려진 한계 (README에 명시 유지)
- `ts_rank_cd`는 **BM25가 아님**. 진짜 BM25가 필요하면 ParadeDB `pg_search` 또는 TigerData `pg_textsearch`로 교체 (스키마 변경 불필요)
- 리랭커(bge-reranker-v2-m3) 미적용
- 회계감사기준·K-IFRS는 법령이 아니라 이 API에 **없음**

## 3. 확인된 API 사실

### 엔드포인트
```
목록: https://www.law.go.kr/DRF/lawSearch.do
본문: https://www.law.go.kr/DRF/lawService.do
```
- 인증: `OC` = 신청 이메일의 @ 앞부분. **별도 발급 키 없음** (`.env`의 `LAW_OC`)
- `type=XML` 권장, `display` 최대 100, `page`로 페이징
- 인증 실패/미승인 시 HTTP 200 + HTML 안내 페이지가 반환됨 → `drf_client.py`가 이미 감지 처리
- 브라우저 User-Agent / Referer 헤더 필요 (설정됨)
- **호출 제한 경고 있음**: 짧은 시간 내 과도한 호출 시 이용 제한. 현재 간격 0.3초 → 대량 수집 시 0.5초로 상향할 것

### 신청 승인된 데이터 범위와 본문 제공 여부 ★중요
| 데이터 | 목록 | 본문 | RAG에서의 역할 |
|---|---|---|---|
| 대한민국 현행법령 | O | **O** | 근거 인용 (조문 전문) |
| 현행 행정규칙 | O | **O** | 근거 인용 (집행기준·외부감사규정) |
| 판례 | O | **O** | 근거 인용 |
| 법령해석례(법제처) | O | **O** | 근거 인용 |
| **조세심판원 특별행정심판례** | O | **O** | 세법 축 **주력 본문** |
| **증권선물위원회** | O | **O** | 감사 축 (회계감리 조치) |
| 금융위원회 | O | **O** | 감사 축 |
| 관세청 법령해석 | O | **O** | 세정 계열 본문 테스트용 |
| **국세청 법령해석** | O | **X (본문 API 없음)** | 안건명 + 링크만 → 참고 표시 |
| **재정경제부 법령해석** | O | **X (본문 API 없음)** | 안건명 + 링크만 → 참고 표시 |
| 법령/행정규칙 별표·서식 | O | HTML만 | 후순위 |
| 지능형 법령정보지식베이스 (용어·연계·관련법령) | O | — | 질의 확장 / relation 채우기 |

### 미확인 (직접 확인 필요)
- 심판례 / 증선위 / 부처별 해석의 **`target=` 코드값**
  → `https://open.law.go.kr/LSO/openApi/guideList.do` 에서 각 API 가이드를 열어 확인할 것.
  → 부처별 해석 가이드는 `guideResult.do?htmlName=cgmExpc{기관}ListGuide` 패턴
  → **추정으로 코드를 넣지 말 것.** 확인 전에는 구현 보류하고 사용자에게 물을 것

## 4. 코퍼스 범위 (의도적으로 좁힘)

**법인세 + 외부감사 2축.** 전체 법령을 넣지 않는다.

- 법인세법 / 시행령 / 시행규칙
- 법인세 집행기준·기본통칙 (행정규칙)
- 주식회사 등의 외부감사에 관한 법률 / 시행령 / 외부감사 및 회계 등에 관한 규정
- 조세심판원 법인세 관련 결정례 **최대 2,000건**
- 증선위 회계 관련 의결 (분량 확인 후 결정)

예상 규모 약 1만~1.2만 청크 / 벡터 50MB 내외.
**국세청 해석 16만건, 심판례 52만건 전체를 긁으면 안 됨.**

## 5. 실행 환경

```bash
LAW_OC        # .env (승인 완료, 값은 사용자가 입력)
DATABASE_URL  # postgresql://lawrag:lawrag@localhost:5433/lawrag
EMBED_BACKEND=local / EMBED_MODEL=BAAI/bge-m3 / EMBED_DIM=1024
```
- BGE-M3 최초 로딩 시 약 2GB 다운로드 발생
- CPU 임베딩 속도 초당 3~10청크 → 1만 청크에 30분~1시간

## 6. 이번 세션 요청

**먼저 계획을 세우고 승인을 받은 뒤 실행할 것.** 아래 우선순위 순.

### P0 — 파이프라인 스모크 테스트
1. `docker compose up -d` → healthy 확인
2. `python -m lawrag.cli init-db`
3. **가장 작은 법령 하나로** ingest (`--query "법인세법 시행규칙" --limit 1`)
4. `search` 로 벡터/키워드 순위가 **양쪽 다** 채워지는지 확인
5. 실패 지점이 있으면 원인을 특정해 수정

> 주의: 법인세법 본법을 처음부터 돌리지 말 것. 파이프라인 검증이 먼저.

### P1 — 스키마 확장: `source_type`
- `chunk` 테이블에 `source_type TEXT NOT NULL DEFAULT 'article'` 추가
  값: `article`(법령·행정규칙) / `decision`(심판례·의결서) / `reference`(본문 없는 해석 - 안건명·링크만)
- `reference` 타입은 LLM 프롬프트에서 **"본문 미제공, 링크만 안내"** 로 다르게 취급
- 기존 데이터 마이그레이션 포함 (idempotent하게)

### P2 — 수집 대상 확장
`drf_client.py`에 아래 메서드 추가. **단, `target` 코드 확인 후 착수.**
- 조세심판원 특별행정심판례 (목록 + 본문)
- 증권선물위원회 결정문 (목록 + 본문)
- 국세청 / 재정경제부 법령해석 (목록만 → `reference` 청크)
- 행정규칙 (목록 + 본문)

`parser.py`에는 결정문용 파서를 별도 함수로 추가 (조문 파서와 분리).
결정문은 조 구조가 없으므로 `주문 / 이유 / 판단` 단위 분할 + 인용 법조문 추출.

### P3 — 평가 스크립트
- `eval/questions.yaml` 을 30문항으로 확장 (법인세 20 + 외부감사 10)
- `python -m lawrag.cli eval` 추가 → **Recall@5, Recall@10, MRR** 출력
- 결과를 README에 표로 기록 (포트폴리오의 핵심 차별점)

### P4 — 질의 확장
- 지능형 법령정보지식베이스의 `일상용어-법령용어 연계` 를 별도 테이블로 적재
- **임베딩하지 말 것.** 질의 전처리 단계에서 조회만 (예: "세금 깎아주는 것" → "조세감면" 추가)
