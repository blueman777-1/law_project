## 1. 이 프로젝트가 하는 일

법제처 국가법령정보 OPEN API(DRF)로 법령을 수집해, **PostgreSQL + pgvector 하나로**
하이브리드 검색을 하고, **문장을 넣으면 저촉 조문과 위법 여부를 조문 인용과 함께** 판단한다.
별도 벡터DB 없음. GitHub 공개 포트폴리오가 목표.

핵심 데모:
```
$ .venv/bin/python -m lawrag.cli check "감사인이 회사의 재무제표를 대신 작성해 주었다"
▸ 판정: 위반 소지 있음  (신뢰도 높음)
▸ 근거: 외부감사법 제6조 제6항 (시행 20250401)   ← 검색 1위, v#2·k#1·t#-
```
(`t#-` 는 이 질의에 일상용어가 없어 용어연계 축이 발화하지 않았다는 뜻이다. 정상이다.)

## 2. 환경 — 왜 이런 선택을 했는가

이 머신(**macOS 13.7.8 Ventura, Intel Kaby Lake, Python 3.14**)의 제약이 설계를 강제했다.
HANDOFF §2 의 "확정 결정" 중 셋을 바꿨고, 전부 사용자 승인을 받았다.

| HANDOFF 원안 | 왜 불가능했나 | 실제로 쓴 것 |
|---|---|---|
| docker-compose pgvector | docker/podman/colima **전부 미설치**. brew 는 Ventura 가 Homebrew 지원 종료라 **bottle 이 하나도 없어**(`bottle tags: []`) cmake 부터 소스 컴파일 → 1~3시간 | **conda-forge** `postgresql=17` + `pgvector` → `pgenv/`. 컴파일 0, 1분, sudo 불필요 |
| BGE-M3 (torch) | Python 3.14 에 **torch 휠 없음** → sentence-transformers·fastembed 모두 불가(onnxruntime 도 없음) | **model2vec** `potion-multilingual-128M` (**256차원**, numpy+tokenizers 만 필요) |
| `ask` LLM 백엔드 | 이 머신에 **API 키가 하나도 없음** | **`claude -p --output-format json --model sonnet`** 서브프로세스 |
| 심판례 2,000건 수집 | `target` 코드 미확인 (HANDOFF §7 이 추정 금지) | 법령 5개만 |
| 스키마 `relation`/`query_log` | 채울 데이터가 없는 빈 테이블 | 만들지 않음 (P2 착수 시 추가) |

> **Postgres.app 은 시도했다 실패했다.** dmg 는 정상(바이트 일치, `koly` 트레일러 확인)이었지만
> `hdiutil attach`/`imageinfo` 가 헤드리스 컨텍스트에서 무한 대기한다(`diskimages-helper` 가
> 아예 안 뜬다). 샌드박스를 꺼도 같다. 다시 시도하지 마라 — conda-forge 로 이미 해결됐다.

`docker-compose.yml` 은 다른 환경 재현용으로 레포에 남겨 뒀다.

### 데이터 흐름

```
적재 ─ DRF API ──► parser ──────► embedder ──► PostgreSQL + pgvector
       (XML)      조 단위 청킹     model2vec     ├─ GIN  (bigram tsvector)
                  900자↑는 항                    ├─ HNSW (vector 256)
                  경계에서만 분할                  └─ token_df (문서빈도)

검색 ─ 질의 ──► 용어 확장 ──┬──► 임베딩 ────────► HNSW  ──┐
                (terms.yaml) │                            │
                             ├──► bigram ─────────► GIN ──┼─► RRF(k=60) ──► claude CLI
                             │    └ df>10% 토큰 제거      │        │
                             └──► 덧붙인 법령용어 ──────────┘   판정 + 조문 인용

세 축의 가중치는 전부 1.0 이다 — 용어연계 축도 벡터·키워드와 동등한 리스트 하나일 뿐,
따로 튜닝하는 노브가 없다. 축이 발화하지 않으면(질의에 일상용어가 없으면)
검색은 기존 2축과 **완전히 동일**하다.

## 5. 절대 깨면 안 되는 불변식

1. **청크 2번째 이후 조각은 반드시 항번호 원문자(①②…)로 시작한다.**
   여기가 깨지면 "제N조 제M항" 인용이 불가능해진다. `chunk_article()` 이 항 경계에서만 자른다.
   항 하나가 900자를 넘어도 쪼개지 않는다 — 인용 가능성 > 크기 균일함.
2. **`조문여부='전문'` 은 조문이 아니라 장 제목**("제1장 총칙")이다. 법인세법 255개 중 42개(16%).
   안 거르면 알맹이 없는 청크가 섞인다. `parse_law()` 가 거른다.
3. **DRF 호출 간격 0.5초 이상.** 0.3초 미만 금지 (HANDOFF §7).
4. **`target` 코드를 추정해서 넣지 마라.** 가이드에서 확인한 것만.
5. **eval 질의를 조문 제목에 가깝게 고쳐 지표를 올리지 마라.** 지금 질의가 어려운 건 의도된 것이다.
6. **코퍼스를 임의로 넓히지 마라.** 법인세 + 외부감사 2축 고정 (`cli.TARGET_LAWS`).
7. **README「알려진 한계」 섹션을 지우지 마라.**
8. **세 축의 RRF 가중치는 전부 1.0 이다. 가중치를 도입하지 마라.**
   가중치를 주면 지표가 조금 오르는 조합이 있지만 전부 회귀를 동반하거나 평탄역이 없다(§7·§9).
   축3 이 안 걸리는 질의에서는 검색이 기존 2축과 **비트 단위로 동일**해야 한다.
   축3 **안쪽** 정렬(핵심용어 → 등장 횟수 → 벡터 거리)은 가중치가 아니라 tie-break 라
   이 불변식과 무관하다. 단조변환을 씌워도 결과가 같아야 한다 — 같지 않으면 그건 노브다.

## 6. 검증된 외부 사실 (추정 아님)

### DRF 기본

- `OC` = 신청 이메일의 @ 앞부분(별도 키 없음). 실제 값은 `.env` 의 `LAW_OC` 에 있다. 승인 완료, 응답 확인함
- 목록 `https://www.law.go.kr/DRF/lawSearch.do` / 본문 `https://www.law.go.kr/DRF/lawService.do`
- 브라우저 User-Agent + `Referer: https://www.law.go.kr/` 헤더 필요
- 인증 실패 시 HTTP 200 + HTML → `drf_client.ensure_xml()` 이 감지

### 법령 본문 XML 구조 (실측)

```

- `항내용` 에는 **이미 항번호(①)가 포함**돼 있다. 따로 붙이지 마라

  (`lstrmRltJoService` 가 아니면 `DrfError`). 다른 target 을 붙일 때도 같은 분기가 필요하다
- **반의어(140302)를 넣으면 안 된다.** `적자`↔`흑자` 라서 질의가 망가진다

  `적자`→결손금 은 `손실금` 을 한 번 더 타야 하고, `회계기간`→사업연도 는
  `lstrmRlt&query=사업연도` 의 **역방향**으로만 이어진다. 양방향 2홉이 필요하다

### lstrmRltJo 응답 구조 (실측 — 8개 용어 전부 받아 봤다)

```
lstrmRltJoService/{target, 키워드, 검색결과개수, 법령용어}
법령용어/{법령용어명, 비고, 용어간관계링크, 연계법령*}
연계법령/{법령명, 조번호, 조가지번호, 조문내용, 용어구분코드, 용어구분, 조문연계용어링크}
```
- `조번호` 는 **4자리 0채움**(`'0059'` = 제59조), `조가지번호` `'05'` = 제75조의5, `'00'` 은 없음
- **같은 조문이 핵심용어·선정용어로 두 번 실려 온다.** 합치지 않으면 축 리스트에
  같은 조문이 두 번 들어가 순위가 왜곡된다. `parse_term_articles()` 가 조문 단위로 묶고
  한 번이라도 140101 이면 핵심용어로 본다
- 응답이 크다: 벌칙 3.0MB/2,360건, 사업연도 3.0MB/1,139건, 기업업무추진비 124KB/39건.
  **검색 때마다 부를 수 없다** — `refresh-terms` 로 미리 받아 `term_article` 에 넣는다
- 실측 건수는 STATE 이전 판의 추정치와 달랐다: 결손금 38→**140**, 사업연도 333→**1,139**

### joRltLstrm 응답 구조 (실측 — 세션 3)

**파라미터가 `lstrmRltJo` 와 정반대다.** `query` 가 용어명이 아니라 **법령명**이고,
`JO`(조번호 6자리)가 **필수**다. 가이드 확인 후 실호출로 검증했다.

```
lawService.do?target=joRltLstrm&query=법인세법&JO=001300     # 001300 = 제13조
JO = 조번호 4자리 + 조가지번호 2자리 (000202 = 제2조의2)
```
```
joRltLstrmService/{target, 키워드, 검색결과개수, 법령조문}
법령조문/{법령명, 조번호, 조가지번호, 조문내용, 연계용어*}
연계용어/{법령용어명, 비고, 용어구분코드, 용어구분, 용어간관계링크, 용어연계조문링크}
```
- **응답이 작다: 조문 하나당 14~21KB.** `lstrmRltJo` 의 3MB 와 대조된다(조문 단위라서).
  대신 **조문마다 한 번씩** 불러야 한다
- **서버가 느리다: 약 13초/건.** 211개 조문에 약 45분. 타임아웃은 넉넉히 줄 것
- **같은 용어가 조문 안 등장 횟수만큼 중복돼 실려 온다.** 제13조는 연계용어 41개인데
  `공제` 6 · `사업연도` 5 · `소득공제액` 5 · `결손금` 2 · `이월결손금` 2 식이다.
  `lstrmRltJo` 쪽 중복(핵심/선정 두 번)과는 성격이 다르니 합치는 규칙을 구분할 것
- **§10 의 제13조 진단이 실측으로 확인됐다**: 제13조의 핵심용어는 `과세표준` **하나뿐**이고
  `결손금`·`이월결손금` 은 선정용어다

## 7. 검색 품질 — 어떻게 여기까지 왔는가

```
문항 30개   Recall@5 0.867   Recall@10 0.933   MRR 0.657   ← 현재 (세션 3에서 30문항으로 확장)
문항 15개   Recall@5 0.867   Recall@10 0.933   MRR 0.684   ← 같은 코드, 옛 문항 집합
```

**아래 표는 전부 15문항 기준 측정 이력이다.** 30문항 숫자와 섞어 읽지 마라 —
분모가 다르다. 개선 여부를 판단할 땐 항상 **같은 문항 집합 안에서** 비교할 것.

| 방식 | R@5 | R@10 | MRR |
|---|---|---|---|
| 벡터 단독 | 0.667 | 0.667 | 0.483 |
| 키워드 단독 | 0.333 | 0.467 | 0.243 |
| 하이브리드 RRF (최초) | 0.533 | 0.667 | 0.466 |
| + 문서빈도 필터 | 0.667 | 0.733 | 0.536 |
| + 용어 사전 질의 확장 | 0.800 | 0.867 | 0.668 |
| + 용어연계 조문 축(3축) | 0.800 | 0.933 | 0.675 |
| **+ 축3 안에서 용어 등장 횟수 tie-break** | **0.867** | **0.933** | **0.684** |

### 고친 것 1 — 문서빈도 필터 (`db.MAX_DF_RATIO = 0.10`)

`법인세율은` 을 bigram 으로 쪼개면 `법인`(청크의 **93%**)·`인세`(**88%**)가 나오는데
변별력 있는 `세율` 은 3% 다. 전부 OR 로 묶으니 `ts_rank_cd` 가 노이즈 밀도로 정렬했다.
df 10% 초과 토큰을 버리자 키워드 축 R@5 가 0.333 → 0.533.
df 는 `ts_stat` 으로 집계해 `token_df` 에 두고 **ingest 마다 갱신**한다
(`db.rebuild_token_df`). 0.5~0.1 이 모두 비슷한 넓은 평탄역이라 15문항 과적합이 아니다.

### 고친 것 2 — 용어 사전 질의 확장 (`lawrag/terms.yaml`, HANDOFF P4)

`접대비` 는 코퍼스에 **0청크**다 — 법이 `기업업무추진비`(19청크)로 개정했기 때문.
없는 단어는 어떤 튜닝으로도 못 찾는다. 확장문을 벡터·키워드 **양쪽**에 쓴다
(한쪽만 쓰면 이득 절반: R@5 0.733 vs 0.800).
사전 항목은 전부 코퍼스 등장 횟수를 세어 보고 넣었다. **새 항목도 반드시 같은 방식으로:**
```sql
SELECT count(*) FROM chunk WHERE text LIKE '%용어%';
```

### 고친 것 3 — 용어연계 조문을 세 번째 축으로 (`term_article`)

질의 확장이 덧붙인 법령용어로 `lstrmRltJo` 연계조문을 찾아, 그 조문의 청크를
세 번째 RRF 리스트로 넣는다. **정렬은 핵심용어(140101) 조문 먼저, 그 안에서 벡터 거리순.**

축을 분리해 재 보니 이 축은 다른 두 축이 못 보는 것을 본다:

| 질의 | 벡터 | 키워드 | 축3 단독 |
|---|---|---|---|
| 회사의 회계기간은 어떻게 정하나요 (제6조) | 14위 | **못 찾음** | **2위** |
| 지난해 적자를 올해 소득에서 빼려면 (제13조) | 24위 | **못 찾음** | 7위 |

그런데 **축 단독 성능이 곧 융합 결과가 아니다.** RRF 는 한 축에만 잡힌 문서를 크게
올리지 못한다 — 축3 7위는 `1/(60+7)=0.0149` 라 다른 청크의 벡터 1위 `1/61=0.0164`
하나에도 밀린다. 그래서 축3 단독 2위였던 회계기간이 융합 후 9위가 된다.

**변형별 15문항 전체 측정** (전부 실행함):

| 축3 구성 | R@5 | R@10 | MRR | 비고 |
|---|---|---|---|---|
| 없음 (2축) | 0.800 | 0.867 | 0.668 | — |
| **핵심용어 먼저 + 선정용어 뒤, w=1.0** | **0.800** | **0.933** | **0.675** | **채택.** 회귀 0 |
| 핵심용어만, w=2.0 | 0.867 | 0.933 | 0.669 | R@5 최고지만 **처벌 문항 1→2위 회귀** |
| 전체 연계조문, w=2.0 | 0.800 | 0.933 | 0.676 | 회귀 0 이나 **w=1.0 에선 무효과**(취약) |
| 핵심/선정 분리 2리스트, wc/wr 9조합 | ≤0.867 | 0.933 | ≤0.678 | 노브만 늘고 이득 없음 |

채택 근거 셋:
1. **회귀 0건.** 핵심용어만 쓰는 변형은 어느 가중치에서도 처벌 문항 1위를 깨뜨린다
   (그 문항의 핵심용어 조문이 1건인데 그게 정답이 아니다)
2. **평탄역.** w=1.0~2.0 이 완전히 동일한 결과다. `all` 은 w=2.0 에서만 작동한다 —
   df 임계값을 평탄역에서 고른 것과 같은 이유로 뾰족한 점을 피했다
3. **노브가 없다.** w=1.0 이면 벡터·키워드와 동등한 리스트 하나일 뿐이라 튜닝할 게 없다

**R@10 천장이 모든 변형에서 0.933(14/15)이었다.** MISS 2건이 동시에 고쳐지는 조합은
하나도 없었고, 가중치에 따라 적자와 회계기간 중 어느 쪽이 고쳐지는지가 뒤바뀐다.
15문항 과적합의 전형적 징후라, 지표를 더 짜내지 않고 회귀 없는 쪽을 골랐다.

### 고친 것 4 — 축3 안에서 용어 등장 횟수로 tie-break (세션 3)

`joRltLstrm` 을 조사하다 나온 부산물이다. 응답에서 같은 용어가 여러 번 실려 오는 걸 보고,
**"이 조문이 그 용어를 실제로 얼마나 다루는가"** 를 정렬에 쓸 수 있다는 걸 알았다.

문제는 이거였다: `사업연도` 핵심용어 조문이 여럿인데 그중 어느 게 제6조인지 가릴 신호가
없어서, 핵심용어 안에서는 벡터 거리가 순서를 정했고 제6조가 뒤로 밀렸다.
조문 본문에 그 용어가 몇 번 나오는지를 두 번째 키로 넣자 제6조가 핵심용어 조문 중 1위가 된다.

```sql
ORDER BY bool_or(t.is_core) DESC,
         max((length(a.body) - length(replace(a.body, t.term,''))) / length(t.term)) DESC,
         min(c.embedding <=> qv)
```

| 축3 정렬 | R@5 | R@10 | MRR | 비고 |
|---|---|---|---|---|
| 핵심먼저 + 벡터순 (세션 2) | 0.800 | 0.933 | 0.675 | — |
| **핵심먼저 + 등장횟수 + 벡터순** | **0.867** | **0.933** | **0.684** | **채택.** 회귀 0 |
| 등장횟수만 + 벡터순 | 0.800 | 0.867 | 0.668 | 회계기간 탈락 |
| 벡터순만 | 0.800 | 0.867 | 0.668 | 회계기간 탈락 |
| 밀도(횟수/본문길이) | 0.800 | 0.933 | 0.679 | 길이 정규화는 오히려 손해 |

채택 근거:
1. **회귀 0건.** 움직인 건 회계기간 9→4위 하나뿐이다
2. **평탄역.** pool 15/30/60/100/200 **전부**에서 기존보다 낫다. `ln(1+x)` 를 씌워도
   결과가 **완전히 동일**하다 — 단조변환이면 순서가 같으니 **튜닝할 값이 아예 없다**
3. **가중치가 아니라 tie-break 라 불변식 8 과 충돌하지 않는다.** 축3 미발화 질의에서는
   RRF 점수가 소수점 12자리까지 기존과 같은 것을 확인했다

**단, 15문항 중 1문항이 움직였을 뿐이다.** 그 자체로는 약한 증거다. §9 의 기각된 변형들과
다른 점은 회귀가 없고 노브가 늘지 않는다는 것이지, 표본이 충분해서가 아니다.

**30문항으로 늘려 다시 쟀다** (세션 3, 같은 세션 안에서):

| 축3 정렬 | R@5 | R@10 | MRR |
|---|---|---|---|
| 핵심먼저 + 벡터순 | 0.833 | 0.933 | 0.653 |
| **핵심먼저 + 등장횟수 + 벡터순** | **0.867** | **0.933** | **0.657** |

결론이 뒤집히지는 않았다 — 30문항에서도 회귀 0건이고 여전히 낫다.
**그런데 움직이는 문항은 두 배로 늘린 뒤에도 똑같이 그 1개다.** 즉 이 재측정으로
확인된 건 "안전하다" 이지 "효과가 크다" 가 아니다. 신규 15문항 중 이 tie-break 가
갈라 주는 문항이 하나도 없었다는 뜻이기도 하다.

**API 횟수(`joRltLstrm` 의 연계용어 중복 수)는 쓰지 않았다.** 본문에서 센 횟수와 다른
신호이긴 하다 — 완전 일치 44.6%, 조문 내 용어쌍 순서가 9.1% 어긋난다. API 는 언급 횟수가
아니라 **연계 지점**을 세는 것으로 보인다(법인세법 제2조 `내국법인`: API 1 / 본문 7).
그런데 프로덕션 설정(pool=30)에서 **지표가 완전히 같았다**(R@5 0.867 / R@10 0.933 / MRR 0.684,
움직인 문항도 동일). 커버리지 부족도 아니었다 — 코퍼스 내 `term_article` 전 행에 API 값이 있었다.
같은 결과라면 컬럼도 수집 경로도 필요 없는 쪽이 낫다. **다시 재려면 조문당 1회씩 211번을
불러야 하고 45분 걸린다**(§6).

## 8. 틀렸던 진단 (같은 실수를 반복하지 말 것)

1. **"시행령이 본법을 밀어낸 라벨 문제"** → 틀렸다. 상위에 온 건 무관한 조문이었다.
2. **"model2vec 정적 임베딩의 한계"** → 틀렸다. 축별로 재보니 **벡터가 키워드보다 나았고**
   (pool 30 밖: 벡터 3건 vs 키워드 6건), **하이브리드가 벡터 단독보다 더 나빴다**(0.533 vs 0.667).
   문제는 임베딩이 아니라 키워드 축이었다.

**교훈: 지표가 나쁠 때 축을 분리해 따로 재보기 전에는 원인을 말하지 마라.**
Step 0 의 임베딩 프로브가 10건짜리 코퍼스라 6/6 Top-1 이 나온 것도 같은 함정이었다 —
1,127청크에서는 전혀 다른 그림이었다.

축별 순위를 재는 스크립트 패턴(재사용 가치 있음): 벡터는 `ORDER BY embedding <=> qv`,
키워드는 `ORDER BY ts_rank_cd(tsv, q) DESC` 로 각각 `ROW_NUMBER()` 를 매기고
정답 조문의 순위를 뽑아 비교한다.

## 9. 시도했다 기각한 것 (다시 하지 마라)

| 시도 | 결과 |
|---|---|
| RRF pool 확대 (30 → 60/100/200/400/1200) | **효과 없음.** R@5 0.533 그대로, R@10 은 오히려 하락 |
| RRF k 조정 (60 → 10/20/30) | 유의미한 차이 없음 |
| 조문 제목에 `setweight('A')`, 본문 'D' | **더 나빠짐.** R@10 0.867→0.800, MRR 0.668→0.633. 목표였던 MISS 2건도 그대로. 임시 컬럼으로 실험 후 롤백함 |
| 축3 을 **핵심용어 조문으로만** 구성 | R@5 는 0.867 로 최고지만 처벌 문항이 1→2위로 회귀. 가중치를 0.3 까지 낮춰도 회귀는 그대로고 이득만 사라진다 |
| 축3 을 **필터로** 사용 (연계조문 밖 청크 제거) | MISS 2건 둘 다 못 고치고, 처벌 문항은 정답이 연계집합 밖이라 **아예 탈락**한다 |
| 축3 을 핵심/선정 **두 리스트로 분리**, 가중치 9조합 | R@10 은 똑같이 0.933 천장. 노브가 둘로 늘 뿐 얻는 게 없다 |
| 축3 을 **등장 횟수만으로** 정렬 (핵심용어 무시) | R@10 0.933→0.867. 회계기간이 아예 탈락한다. 핵심용어 우선은 남겨야 한다 |
| 등장 횟수를 **본문 길이로 정규화**(밀도) | R@5 0.867→0.800. 긴 조문 페널티가 손해다. raw 횟수가 낫다 |
| tie-break 를 **API 횟수**(`joRltLstrm`)로 | 프로덕션 설정에서 본문 횟수와 지표가 **완전히 동일**. 컬럼·수집 경로(45분)만 늘어난다 (§7) |

## 11. 함정 (모르면 시간 낭비함)

- **전역 TDD 훅이 켜져 있다.** `~/.claude/hooks/tdd-autotest.py` 가 `pyproject.toml` 을 보고
  Write/Edit 마다 pytest 를 돌리고 **실패하면 다음 작업을 막는다.** 방해가 아니라 안전망이니
  끄지 말고 테스트를 먼저 써라. 탈출구는 `CLAUDE_TDD_HOOK=0` 또는 `.no-tdd` 파일이지만 쓰지 마라.
  `~/.claude/hooks/tdd-guard.py` 는 테스트 비활성화/삭제만 막는다.
- **`embed_one()` 은 numpy 배열을 반환해야 한다.** 파이썬 list 로 넘기면 psycopg 가
  `double precision[]` 로 어댑트해서 pgvector 의 `<=>` 가 안 걸린다. 실제로 여기서 한 번 깨졌다.
- **eval 의 법령명은 정확일치로 비교한다.** 부분일치로 하면 `법인세법` 이 `법인세법 시행령` 에도
  걸려서, 양쪽에 다 있는 제6조가 오탐이 된다.
- **`ingest --query` 는 정확일치 법령만 적재한다.** 검색이 부분일치라 '법인세법'으로
  시행령까지 딸려오기 때문.
- **`refresh-terms` 는 서버가 매달리면 몇십 분씩 안 끝난다.** 실제로 겪었다: HTTPS 연결은
  ESTABLISHED 인데 데이터가 안 오고 CPU 0%. requests 의 `timeout` 은 **읽기 사이 간격**이라
  서버가 찔끔찔끔 보내면 안 걸린다. 용어마다 즉시 커밋되고 **이미 받은 용어는 건너뛰므로,
  끊기면 그냥 다시 돌려라**(`--force` 를 줘야 전부 다시 받는다). 큰 응답 4개(벌칙·벌금·
  징역·사업연도, 각 2~3MB)가 문제다.
- **`lstrmRltJo` 는 응답이 커서 기본 30초 타임아웃으로는 실패한다.** `fetch_term_articles()`
  가 180초를 쓴다. 다른 target 을 붙일 때도 응답 크기를 먼저 재 볼 것.
- **`term_article` 데이터는 DB 에만 있다.** 세션 2 에서 쓴 응답 XML 캐시는 세션 임시 디렉터리라
  이미 사라졌다. 이 테이블을 비우면 **다시 네트워크로 받는 수밖에 없다** — 함부로
  `TRUNCATE` 하지 마라. 백업이 필요하면 `pg_dump -t term_article`.
- **Bash 툴의 `grep` 은 셸 함수로 가려져 있다** (`~/.claude/shell-snapshots/…` 가 정의).
  실제로 매치가 있는데 **조용히 0건을 반환**했다. `git grep` 도 같은 증상이 났다.
  비밀값 스캔처럼 "0건" 이 곧 결론이 되는 검사는 **`/usr/bin/grep` 절대경로**를 써라.
  일반 코드 탐색은 Grep 툴을 쓰면 된다.
- **픽스처 XML 에 실제 API 응답의 `OC` 값이 섞여 들어간다.** `lawSearch_sample.xml` 의
  `법령상세링크` 에 `OC=<실제값>` 이 3건 박혀 있었다(첫 커밋 직전에 `your_email_id` 로 치환).
  응답을 새로 떠서 픽스처로 넣을 때마다 이 필드를 확인할 것.
- 서브에이전트가 **API 연결 오류로 죽는 일이 있었다**(작업 실패가 아님). 결과가 안 오면 다시 띄워라.
  `.claude/agents/` 에 `law-api-prober` / `corpus-inspector` / `retrieval-evaluator` 3개가 있다.

## 12. 컨텍스트 관리

`.claude/settings.local.json` 에 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=50` 이 들어 있다.
**훅으로 자동 compact 는 불가능하다** — 컨텍스트 사용량을 받는 훅 이벤트가 없고
compact 를 시키는 출력 필드도 없다. 이 env 는 **세션 시작 시** 읽히므로 다음 세션부터 적용된다.
이 파일만 지우면 원복된다.

운영 방식: **알아낸 것은 즉시 이 문서에 적고, 작업 경계에서 `/clear`.**
컨텍스트를 지식 저장소로 쓰지 마라 — 요약은 숫자와 고유명사를 가장 먼저 버린다.
긴 XML·psql 덤프는 서브에이전트에 격리한다.
