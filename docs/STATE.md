## 1. 이 프로젝트가 하는 일

법제처 국가법령정보 OPEN API(DRF)로 법령을 수집해, **PostgreSQL + pgvector 하나로**
하이브리드 검색을 하고, **문장을 넣으면 저촉 조문과 위법 여부를 조문 인용과 함께** 판단한다.
별도 벡터DB 없음. GitHub 공개 포트폴리오가 목표.

핵심 데모:
```
$ .venv/bin/python -m lawrag.cli check "감사인이 회사의 재무제표를 대신 작성해 주었다"
▸ 판정: 위반 소지 있음  (신뢰도 높음)
▸ 근거: 외부감사법 제6조 제6항 (시행 20250401)   ← 검색 1위, v#2·k#1·t#-
```
(`t#-` 는 이 질의에 일상용어가 없어 용어연계 축이 발화하지 않았다는 뜻이다. 정상이다.)

## 2. 환경 — 왜 이런 선택을 했는가

이 머신(**macOS 13.7.8 Ventura, Intel Kaby Lake, Python 3.14**)의 제약이 설계를 강제했다.
HANDOFF §2 의 "확정 결정" 중 셋을 바꿨고, 전부 사용자 승인을 받았다.

| HANDOFF 원안 | 왜 불가능했나 | 실제로 쓴 것 |
|---|---|---|
| docker-compose pgvector | docker/podman/colima **전부 미설치**. brew 는 Ventura 가 Homebrew 지원 종료라 **bottle 이 하나도 없어**(`bottle tags: []`) cmake 부터 소스 컴파일 → 1~3시간 | **conda-forge** `postgresql=17` + `pgvector` → `pgenv/`. 컴파일 0, 1분, sudo 불필요 |
| BGE-M3 (torch) | Python 3.14 에 **torch 휠 없음** → sentence-transformers·fastembed 모두 불가(onnxruntime 도 없음) | **model2vec** `potion-multilingual-128M` (**256차원**, numpy+tokenizers 만 필요) |
| `ask` LLM 백엔드 | 이 머신에 **API 키가 하나도 없음** | **`claude -p --output-format json --model sonnet`** 서브프로세스 |

## 5. 절대 깨면 안 되는 불변식

1. **청크 2번째 이후 조각은 반드시 항번호 원문자(①②…)로 시작한다.**
   여기가 깨지면 "제N조 제M항" 인용이 불가능해진다. `chunk_article()` 이 항 경계에서만 자른다.
   항 하나가 900자를 넘어도 쪼개지 않는다 — 인용 가능성 > 크기 균일함.
2. **`조문여부='전문'` 은 조문이 아니라 장 제목**("제1장 총칙")이다. 법인세법 255개 중 42개(16%).
   안 거르면 알맹이 없는 청크가 섞인다. `parse_law()` 가 거른다.
3. **DRF 호출 간격 0.5초 이상.** 0.3초 미만 금지 (HANDOFF §7).
4. **`target` 코드를 추정해서 넣지 마라.** 가이드에서 확인한 것만.
5. **eval 질의를 조문 제목에 가깝게 고쳐 지표를 올리지 마라.** 지금 질의가 어려운 건 의도된 것이다.
6. **코퍼스를 임의로 넓히지 마라.** 법인세 + 외부감사 2축 고정 (`cli.TARGET_LAWS`).
   **자료 종류도 조문만이다** — 결정문·해석·행정규칙은 세션 5 에 넣지 않기로 확정했다.
   측정 근거는 §10 의 「P2 종결」 상자에 있다. 수집 코드는 남아 있지만 돌리지 마라.
7. **README「알려진 한계」 섹션을 지우지 마라.**
8. **세 축의 RRF 가중치는 전부 1.0 이다. 가중치를 도입하지 마라.**
   가중치를 주면 지표가 조금 오르는 조합이 있지만 전부 회귀를 동반하거나 평탄역이 없다(§7·§9).
   축3 이 안 걸리는 질의에서는 검색이 기존 2축과 **비트 단위로 동일**해야 한다.
   축3 **안쪽** 정렬(핵심용어 → 등장 횟수 → 벡터 거리)은 가중치가 아니라 tie-break 라
   이 불변식과 무관하다. 단조변환을 씌워도 결과가 같아야 한다 — 같지 않으면 그건 노브다.
9. **세 축 CTE 의 정렬은 마지막 키가 기본키(`id`)여야 한다.** 창 함수의 `ORDER BY` 와
   `LIMIT` 의 `ORDER BY` 는 **글자 그대로 같아야 한다** — 어긋나면 풀에 남은 행의 rank 가
   1..pool 이 아니게 된다. `tests/test_hybrid_sql.py` 가 둘 다 지킨다. 근거는 §7 고친 것 9.

## 6. 검증된 외부 사실 (추정 아님)

### DRF 기본

- `OC` = 신청 이메일의 @ 앞부분(별도 키 없음). 실제 값은 `.env` 의 `LAW_OC` 에 있다. 승인 완료, 응답 확인함
- 목록 `https://www.law.go.kr/DRF/lawSearch.do` / 본문 `https://www.law.go.kr/DRF/lawService.do`
- 브라우저 User-Agent + `Referer: https://www.law.go.kr/` 헤더 필요
- 인증 실패 시 HTTP 200 + HTML → `drf_client.ensure_xml()` 이 감지

### 법령 본문 XML 구조 (실측)

```
법령/기본정보/{법령ID, 법령명_한글, 법종구분, 소관부처, 공포일자, 시행일자}
법령/조문/조문단위/{조문번호, 조문가지번호, 조문여부, 조문제목, 조문내용, 조문시행일자,
                  항/{항번호, 항내용, 호/{호내용}}}
```
- `항내용` 에는 **이미 항번호(①)가 포함**돼 있다. 따로 붙이지 마라
- `호` 텍스트는 `항내용` 에 **중복되지 않는다**
- **`항번호`가 비어 있고 `호`만 있는 조문**이 있다 (예: 법인세법 제2조 정의)
- 법인세법 기준 조문단위 255 = 조문 213 + 전문 42, 그중 99개가 가지번호(제18조의2), 36개가 900자 초과

|---|---|---|---|
| `ttSpecialDecc` | 조세심판원 결정문 | **있음** | specialDeccTtListGuide / specialDeccTtInfoGuide |
| `admrul` | 행정규칙(고시·훈령·예규) | **있음** | admrulListGuide / admrulInfoGuide |
| `sfc` | 증권선물위원회 의결 | **있음** | sfcListGuide / sfcInfoGuide |

법령해석 2종에 본문 API 가 없다는 것은 **실측으로도 확인**됐다 — `lawService.do` 를 부르면
XML 이 아니라 HTML 안내 페이지(1,649B)가 온다. README 「알려진 한계」의 기술이 맞았다.

**응답 크기는 문제가 안 된다** (§11 의 `lstrmRltJo` 3MB 사례와 대조):
중앙값 `ttSpecialDecc` 24KB / `admrul` 7.7KB / `sfc` 1.2KB, 최대 375KB, 전부 1.6초 이내.

**범위를 좁히는 수단 (불변식 6 판단에 쓸 것)**

| target | 좁히는 수단 | 결과 건수 |
|---|---|---|
| `admrul` | `org=1210000`(국세청) / `org=1160100`(금융위) | 199 + 134 = 333건, 약 2.7MB |
| `sfc` | `query` 뿐 | 전체 868건 / 약 1MB (좁힐 필요 없는 크기) |
| `ttSpecialDecc` | `query=법인세`(사건명 검색) | 2,827건. 약 68MB, 0.8초 간격이면 38분 |
| `ttSpecialDecc` | 위 + `rslYd=20200101~20251231` | 791건 |

**주의 2가지 (세션 4 실측)**
- **`admrul` 의 `org` 코드표는 가이드에 없다** ("코드별도제공" 이라고만 적혀 있다).
  위 두 값은 **추정이 아니라** 본문 응답의 `소관부처코드` 필드에서 얻어 `org=` 필터로
  역검증한 것이다. 다만 **공식 코드표 자체는 확인 불가**라, 다른 부처 코드가 필요하면
  같은 방식으로 하나씩 실측해야 한다. `target` 코드와 달리 이건 가이드 근거가 아니다
- **`ttSpecialDecc` 의 `세목` 은 본문 응답에만 있고 목록에는 없다.** `fields=세목` 을 목록에
  넣으면 **에러 없이 조용히 무시된다.** 세목 기준 필터링은 본문을 받아야만 가능하다.
  `cls` 는 전 레코드가 `429150`("조세") 단일값이라 필터로 쓸모가 없다

### 결정문 API 응답 구조 (실측 — 세션 4)

두 target 모두 **목록 → `ID` → 본문** 으로 같은 모양이다. 본문 조회 파라미터는 `ID` 다
(목록의 상세링크에서 확인. `MST` 가 아니다).

```
목록  Decc/decc/{특별행정심판재결례일련번호, 사건명, 청구번호, 의결일자, 재결청,
                재결구분명, 재결구분코드, 행정심판재결례상세링크, 데이터기준일시}
본문  SpecialDeccService/{특별행정심판재결례일련번호, 사건명, 사건번호, 청구번호, 의결일자,
                재결청, 재결례유형명, 재결례유형코드, 세목, 재결요지, 따른결정, 참조결정,
                주문, 청구취지, 이유, 관련법령, 데이터기준일시}
목록  Sfc/sfc/{결정문일련번호, 기관명, 안건명, 의결번호, 결정문상세링크}
본문  SfcService/{결정문일련번호, 기관명, 의결번호, 안건명,
                조치대상자의인적사항, 조치내용, 조치이유}
```

- **일련번호가 숫자다**(`950990`, `8259`). `article.article_no` 를 여기서 결정적으로 채울 수
  있다 — 순번을 쓰면 재적재 때 다른 결정문을 덮어쓴다
- **본문의 `청구번호`·`사건번호` 는 항상 비어 있다** (2020~2025 표본 전부). 사건번호는
  **목록에서만** 온다. `label` 을 채우려면 목록 값을 본문 파싱까지 들고 가야 한다
- 날짜 형식이 다르다: 목록 `'2024.10.21'` / 본문 `'20241021'`. **본문 쪽을 써라** — 정규화 불필요
- 본문 텍스트는 **여러 필드로 쪼개져** 온다. tt: 재결요지·주문·청구취지·이유·관련법령 /
  sfc: 조치대상자의인적사항·조치내용·조치이유. **조(條) 구조는 없다**
- sfc 도 **전문이 온다**(조치내용·조치이유, 0.6~1.4KB). `reference` 가 아니라 `decision` 이 맞다
- 본문 길이 실측: tt 3.9~14.5KB(4건), sfc 0.6~1.4KB(4건). HTML 엔티티(`&nbsp;` 등)는 **없다**

**착수 전 반드시 알아야 할 함정 4가지**
- **`rslYd` 를 잘못 쓰면 에러 없이 조용히 무시된다.** `20200101~20251231` 은 791건으로
  걸리지만 `~` 를 `%7E` 로 인코딩하면 필터가 통째로 무시되고 전체 2,827건이 돌아온다.
  **건수를 확인하지 않으면 모르고 지나간다**
- **`<...>` 를 통째로 지우면 실제 내용이 사라진다.** tt 본문에는 진짜 HTML 이 섞여 있지만
  (`p` 40 · `span` 38 · `td` 12 · `a` 12 · `tr` 8 · `table`/`tbody` 6, 4건 기준),
  sfc 에는 **태그가 아닌 꺾쇠**가 내용으로 들어 있다 — `< 외부감사인 >`·`< 기관 >`·
  `< 대표이사 >`·`< ☆☆회계법인 >` 같은 소제목과 마스킹된 상호 `<OO>`.
  **HTML 태그명 화이트리스트로만 지워라.** 정규식 `<[^>]*>` 는 금지다
- **`query=법인세` 는 사건명 검색이라 세목이 섞인다.** 표본 3건 중 1건이 `세목='지방소득'`
  이었다. 세목은 본문에만 있지만 **어차피 본문을 받으므로 추가 비용 없이 거를 수 있다**
- **없는 `ID` 를 부르면 루트가 `<Law>`** 로 온다(`일치하는 조세심판원 특별행정심판재결례이
  없습니다`). `lstrmRltJo` 와 같은 함정이라 **루트 태그 가드가 필요하다**
  (`SpecialDeccService` / `SfcService`). 목록 쪽 결과 0건은 루트가 그대로 `<Decc>` 에
  `totalCnt=0` 이라 가드가 아니라 건수로 판정한다

**페이징**: `display` 최대 **100** (200 을 줘도 100 만 온다), `page` 는 1부터.
791건이면 8페이지, 868건이면 9페이지. 본문은 건당 1회씩이라 0.5초 간격으로 tt 약 7분 +
sfc 약 7분이다.

**착수 전 반드시 알아야 할 함정 4가지**
- `dlytrm`/`lstrmAI`(lawSearch)는 부분일치지만 `dlytrmRlt`/`lstrmRlt`(lawService)의 `query` 는
  **정확일치**다. 안전한 순서: `dlytrm` 으로 후보+MST 확보 → MST 로 연계 조회
- 결과 없음일 때도 HTTP 200 + `<?xml ...?><Law>일치하는 일상용어가 없습니다…</Law>` 가 온다.
  `ensure_xml()` 은 이걸 통과시킨다. **`parse_term_articles()` 에는 루트 태그 판정을 넣었다**
  (`lstrmRltJoService` 가 아니면 `DrfError`). 다른 target 을 붙일 때도 같은 분기가 필요하다
- **반의어(140302)를 넣으면 안 된다.** `적자`↔`흑자` 라서 질의가 망가진다
- 1홉으론 부족하다: `접대비`→기업업무추진비, `처벌`→벌칙 은 1홉이지만
  `적자`→결손금 은 `손실금` 을 한 번 더 타야 하고, `회계기간`→사업연도 는
  `lstrmRlt&query=사업연도` 의 **역방향**으로만 이어진다. 양방향 2홉이 필요하다

### lstrmRltJo 응답 구조 (실측 — 8개 용어 전부 받아 봤다)

```
lstrmRltJoService/{target, 키워드, 검색결과개수, 법령용어}
법령용어/{법령용어명, 비고, 용어간관계링크, 연계법령*}
연계법령/{법령명, 조번호, 조가지번호, 조문내용, 용어구분코드, 용어구분, 조문연계용어링크}
```
- `조번호` 는 **4자리 0채움**(`'0059'` = 제59조), `조가지번호` `'05'` = 제75조의5, `'00'` 은 없음
- **같은 조문이 핵심용어·선정용어로 두 번 실려 온다.** 합치지 않으면 축 리스트에
  같은 조문이 두 번 들어가 순위가 왜곡된다. `parse_term_articles()` 가 조문 단위로 묶고
  한 번이라도 140101 이면 핵심용어로 본다
- 응답이 크다: 벌칙 3.0MB/2,360건, 사업연도 3.0MB/1,139건, 기업업무추진비 124KB/39건.
  **검색 때마다 부를 수 없다** — `refresh-terms` 로 미리 받아 `term_article` 에 넣는다
- 실측 건수는 STATE 이전 판의 추정치와 달랐다: 결손금 38→**140**, 사업연도 333→**1,139**

### joRltLstrm 응답 구조 (실측 — 세션 3)

**파라미터가 `lstrmRltJo` 와 정반대다.** `query` 가 용어명이 아니라 **법령명**이고,
`JO`(조번호 6자리)가 **필수**다. 가이드 확인 후 실호출로 검증했다.

```
lawService.do?target=joRltLstrm&query=법인세법&JO=001300     # 001300 = 제13조
JO = 조번호 4자리 + 조가지번호 2자리 (000202 = 제2조의2)
```
```
joRltLstrmService/{target, 키워드, 검색결과개수, 법령조문}
법령조문/{법령명, 조번호, 조가지번호, 조문내용, 연계용어*}
연계용어/{법령용어명, 비고, 용어구분코드, 용어구분, 용어간관계링크, 용어연계조문링크}
```
- **응답이 작다: 조문 하나당 14~21KB.** `lstrmRltJo` 의 3MB 와 대조된다(조문 단위라서).
  대신 **조문마다 한 번씩** 불러야 한다
- **서버가 느리다: 약 13초/건.** 211개 조문에 약 45분. 타임아웃은 넉넉히 줄 것
- **같은 용어가 조문 안 등장 횟수만큼 중복돼 실려 온다.** 제13조는 연계용어 41개인데
  `공제` 6 · `사업연도` 5 · `소득공제액` 5 · `결손금` 2 · `이월결손금` 2 식이다.
  `lstrmRltJo` 쪽 중복(핵심/선정 두 번)과는 성격이 다르니 합치는 규칙을 구분할 것
- **§10 의 제13조 진단이 실측으로 확인됐다**: 제13조의 핵심용어는 `과세표준` **하나뿐**이고
  `결손금`·`이월결손금` 은 선정용어다

### lstrmRlt / dlytrmRlt 응답 구조 (실측 — 세션 3)

```
lstrmRltService/법령용어*/{법령용어명, 비고, 연계용어*/{일상용어명, 용어관계코드, 용어관계}}
dlytrmRltService/일상용어*/{일상용어명, 출처, 연계용어*/{법령용어명, 비고, 용어관계코드, 용어관계}}
```
- 응답이 작다(2~8KB). `trmRltCd` 를 **요청 파라미터로 넘길 수 있어** 반의어를 아예 안 받을 수 있다
- **`<법령용어>` 가 뜻마다 반복된다.** 이게 동음이의어 구분 장치다 — §11 의 함정 참고
- 결과 없으면 루트가 `<Law>` 다. 여기도 루트 태그 가드가 필요하다
- **연계는 방향에 따라 다르다** (§6 함정 4 의 실증): `지배회사`→`모회사` 가 있고

  `계열사`→`특수관계인` 도 **없다**. API 가 안 놓은 다리는 양방향 어디에도 없다
- **반의어가 실제로 섞여 온다**: `모회사`↔`자회사`, `자회사`↔`모회사` 가 140302 로 걸려 있다.
  안 걸렀으면 `모회사`→`자회사` 가 사전에 들어갈 뻔했다 (`적자`↔`흑자` 와 같은 사고)

## 7. 검색 품질 — 어떻게 여기까지 왔는가

```
세대 D  문항 50개   Recall@5 0.720   Recall@10 0.780   MRR 0.547   ← 현재 (세션 6 말)
──────── 여기서 문항 30 → 50. 분모가 다르다 (§7 고친 것 10) ────────
세대 C  문항 30개   Recall@5 0.900   Recall@10 0.967   MRR 0.679   ← 세션 5 말. 회귀 확인용으로 계속 쓴다
──────── 여기서 tie-break 도입. 아래 수치와 직접 비교 금지 (§7 고친 것 9) ────────
세대 B  문항 30개   Recall@5 0.900   Recall@10 0.967   MRR 0.692   ← 세션 4 말
세대 B  문항 30개   Recall@5 0.900   Recall@10 0.933   MRR 0.685   ← 세션 4 시작 시점
세대 B  문항 30개   Recall@5 0.867   Recall@10 0.933   MRR 0.657   ← 사전 확장(§7 고친 것 5) 직전
```
> **세대 B 의 위 두 줄 사이에는 코드도 데이터도 바뀐 게 없다.** 결정문을 넣었다 지우면서
> 키워드 축의 동점 순서가 재배치된 것뿐이다. **개선이 아니다** — §7 고친 것 8 을 읽어라.
>
> **세대 구분 — 분모도 다르고 결정성도 다르다. 셋을 섞어 읽지 마라.**
>
> | 세대 | 문항 | 동점 처리 | 수치의 성격 |
> |---|---|---|---|
> | A | 15 | 없음 | 아래 15문항 표. 분모가 다르다 |
> | B | 30 | 없음 | **재현되지 않는다.** 같은 데이터가 0.685·0.692 를 둘 다 냈다 |
> | C | 30 | `id` tie-break | 재현된다. **회귀 확인용으로 계속 쓴다** (50문항의 앞 30개) |
> | D | 50 | `id` tie-break | **지금 기준선.** 문항 선정이 중립적인 첫 세대 (§7 고친 것 10) |

**아래 표는 전부 세대 A(15문항, 동점 처리 없음) 측정 이력이다.** 30문항 숫자와 섞어 읽지
마라 — 분모가 다르다. 개선 여부를 판단할 땐 항상 **같은 세대 안에서** 비교할 것.
세대 A·B 의 "1문항 움직임" 결론들은 tie 재배치와 구분되지 않는다 — §7 고친 것 9 를 읽어라.

| 방식 | R@5 | R@10 | MRR |
|---|---|---|---|

### 고친 것 1 — 문서빈도 필터 (`db.MAX_DF_RATIO = 0.10`)

`법인세율은` 을 bigram 으로 쪼개면 `법인`(청크의 **93%**)·`인세`(**88%**)가 나오는데
변별력 있는 `세율` 은 3% 다. 전부 OR 로 묶으니 `ts_rank_cd` 가 노이즈 밀도로 정렬했다.
df 10% 초과 토큰을 버리자 키워드 축 R@5 가 0.333 → 0.533.
df 는 `ts_stat` 으로 집계해 `token_df` 에 두고 **ingest 마다 갱신**한다
(`db.rebuild_token_df`). 0.5~0.1 이 모두 비슷한 넓은 평탄역이라 15문항 과적합이 아니다.

### 고친 것 2 — 용어 사전 질의 확장 (`lawrag/terms.yaml`, HANDOFF P4)

`접대비` 는 코퍼스에 **0청크**다 — 법이 `기업업무추진비`(19청크)로 개정했기 때문.
없는 단어는 어떤 튜닝으로도 못 찾는다. 확장문을 벡터·키워드 **양쪽**에 쓴다
(한쪽만 쓰면 이득 절반: R@5 0.733 vs 0.800).
사전 항목은 전부 코퍼스 등장 횟수를 세어 보고 넣었다. **새 항목도 반드시 같은 방식으로:**
```sql
SELECT count(*) FROM chunk WHERE text LIKE '%용어%';
```

### 고친 것 3 — 용어연계 조문을 세 번째 축으로 (`term_article`)

질의 확장이 덧붙인 법령용어로 `lstrmRltJo` 연계조문을 찾아, 그 조문의 청크를
세 번째 RRF 리스트로 넣는다. **정렬은 핵심용어(140101) 조문 먼저, 그 안에서 벡터 거리순.**

축을 분리해 재 보니 이 축은 다른 두 축이 못 보는 것을 본다:

| 질의 | 벡터 | 키워드 | 축3 단독 |
|---|---|---|---|
| 회사의 회계기간은 어떻게 정하나요 (제6조) | 14위 | **못 찾음** | **2위** |
| 지난해 적자를 올해 소득에서 빼려면 (제13조) | 24위 | **못 찾음** | 7위 |

그런데 **축 단독 성능이 곧 융합 결과가 아니다.** RRF 는 한 축에만 잡힌 문서를 크게
올리지 못한다 — 축3 7위는 `1/(60+7)=0.0149` 라 다른 청크의 벡터 1위 `1/61=0.0164`
하나에도 밀린다. 그래서 축3 단독 2위였던 회계기간이 융합 후 9위가 된다.

**변형별 15문항 전체 측정** (전부 실행함):

| 축3 구성 | R@5 | R@10 | MRR | 비고 |
|---|---|---|---|---|
| 없음 (2축) | 0.800 | 0.867 | 0.668 | — |
| **핵심용어 먼저 + 선정용어 뒤, w=1.0** | **0.800** | **0.933** | **0.675** | **채택.** 회귀 0 |
| 핵심용어만, w=2.0 | 0.867 | 0.933 | 0.669 | R@5 최고지만 **처벌 문항 1→2위 회귀** |
| 전체 연계조문, w=2.0 | 0.800 | 0.933 | 0.676 | 회귀 0 이나 **w=1.0 에선 무효과**(취약) |
| 핵심/선정 분리 2리스트, wc/wr 9조합 | ≤0.867 | 0.933 | ≤0.678 | 노브만 늘고 이득 없음 |

채택 근거 셋:
1. **회귀 0건.** 핵심용어만 쓰는 변형은 어느 가중치에서도 처벌 문항 1위를 깨뜨린다
   (그 문항의 핵심용어 조문이 1건인데 그게 정답이 아니다)
2. **평탄역.** w=1.0~2.0 이 완전히 동일한 결과다. `all` 은 w=2.0 에서만 작동한다 —
   df 임계값을 평탄역에서 고른 것과 같은 이유로 뾰족한 점을 피했다
3. **노브가 없다.** w=1.0 이면 벡터·키워드와 동등한 리스트 하나일 뿐이라 튜닝할 게 없다

**R@10 천장이 모든 변형에서 0.933(14/15)이었다.** MISS 2건이 동시에 고쳐지는 조합은
하나도 없었고, 가중치에 따라 적자와 회계기간 중 어느 쪽이 고쳐지는지가 뒤바뀐다.
15문항 과적합의 전형적 징후라, 지표를 더 짜내지 않고 회귀 없는 쪽을 골랐다.

### 고친 것 4 — 축3 안에서 용어 등장 횟수로 tie-break (세션 3)

`joRltLstrm` 을 조사하다 나온 부산물이다. 응답에서 같은 용어가 여러 번 실려 오는 걸 보고,
**"이 조문이 그 용어를 실제로 얼마나 다루는가"** 를 정렬에 쓸 수 있다는 걸 알았다.

문제는 이거였다: `사업연도` 핵심용어 조문이 여럿인데 그중 어느 게 제6조인지 가릴 신호가
없어서, 핵심용어 안에서는 벡터 거리가 순서를 정했고 제6조가 뒤로 밀렸다.
조문 본문에 그 용어가 몇 번 나오는지를 두 번째 키로 넣자 제6조가 핵심용어 조문 중 1위가 된다.

```sql
ORDER BY bool_or(t.is_core) DESC,
         max((length(a.body) - length(replace(a.body, t.term,''))) / length(t.term)) DESC,
         min(c.embedding <=> qv)
```

| 축3 정렬 | R@5 | R@10 | MRR | 비고 |
|---|---|---|---|---|
| 핵심먼저 + 벡터순 (세션 2) | 0.800 | 0.933 | 0.675 | — |
| **핵심먼저 + 등장횟수 + 벡터순** | **0.867** | **0.933** | **0.684** | **채택.** 회귀 0 |
| 등장횟수만 + 벡터순 | 0.800 | 0.867 | 0.668 | 회계기간 탈락 |
| 벡터순만 | 0.800 | 0.867 | 0.668 | 회계기간 탈락 |
| 밀도(횟수/본문길이) | 0.800 | 0.933 | 0.679 | 길이 정규화는 오히려 손해 |

채택 근거:
1. **회귀 0건.** 움직인 건 회계기간 9→4위 하나뿐이다
2. **평탄역.** pool 15/30/60/100/200 **전부**에서 기존보다 낫다. `ln(1+x)` 를 씌워도
   결과가 **완전히 동일**하다 — 단조변환이면 순서가 같으니 **튜닝할 값이 아예 없다**
3. **가중치가 아니라 tie-break 라 불변식 8 과 충돌하지 않는다.** 축3 미발화 질의에서는
   RRF 점수가 소수점 12자리까지 기존과 같은 것을 확인했다

**단, 15문항 중 1문항이 움직였을 뿐이다.** 그 자체로는 약한 증거다. §9 의 기각된 변형들과
다른 점은 회귀가 없고 노브가 늘지 않는다는 것이지, 표본이 충분해서가 아니다.

**30문항으로 늘려 다시 쟀다** (세션 3, 같은 세션 안에서):

| 축3 정렬 | R@5 | R@10 | MRR |
|---|---|---|---|
| 핵심먼저 + 벡터순 | 0.833 | 0.933 | 0.653 |
| **핵심먼저 + 등장횟수 + 벡터순** | **0.867** | **0.933** | **0.657** |

결론이 뒤집히지는 않았다 — 30문항에서도 회귀 0건이고 여전히 낫다.
**그런데 움직이는 문항은 두 배로 늘린 뒤에도 똑같이 그 1개다.** 즉 이 재측정으로
확인된 건 "안전하다" 이지 "효과가 크다" 가 아니다. 신규 15문항 중 이 tie-break 가
갈라 주는 문항이 하나도 없었다는 뜻이기도 하다.

**API 횟수(`joRltLstrm` 의 연계용어 중복 수)는 쓰지 않았다.** 본문에서 센 횟수와 다른
신호이긴 하다 — 완전 일치 44.6%, 조문 내 용어쌍 순서가 9.1% 어긋난다. API 는 언급 횟수가
아니라 **연계 지점**을 세는 것으로 보인다(법인세법 제2조 `내국법인`: API 1 / 본문 7).
그런데 프로덕션 설정(pool=30)에서 **지표가 완전히 같았다**(R@5 0.867 / R@10 0.933 / MRR 0.684,
움직인 문항도 동일). 커버리지 부족도 아니었다 — 코퍼스 내 `term_article` 전 행에 API 값이 있었다.
같은 결과라면 컬럼도 수집 경로도 필요 없는 쪽이 낫다. **다시 재려면 조문당 1회씩 211번을
불러야 하고 45분 걸린다**(§6).

움직인 건 「모회사가 연결재무제표를 만들려고 자회사 장부를 요구」 1문항이다(6위 → 1위).

**두 효과를 분리해 쟀다** — 사전을 고쳐도 `refresh-terms` 를 안 돌리면 축3은 그대로다.

**선정을 eval 이 아니라 코퍼스에서 출발시킨 것이 핵심이다.** 실패 문항을 보고 그 단어를

1. 코퍼스 조문에 붙어 있는 법령용어를 `joRltLstrm` 으로 모아 빈도순 정렬

4. 코퍼스 등장 횟수를 세어 확인 — 일상어는 드물고 법령용어는 흔할 것

이 절차가 중립적이라는 증거: **`모회사`→`지배회사` 를 파이프라인이 스스로 찾아냈다.**
코퍼스 빈도만으로 도달한 경로지, eval 실패를 보고 넣은 게 아니다.

**정직하게 적어 둘 것 둘.**
- 법제처 "일상용어" DB는 기대만큼 구어적이지 않다. 동의어만 추려도 `국내발생소득`·
  `총출자액` 처럼 사람이 칠 리 없는 형태 변형이 상당수다. `접대비→기업업무추진비` 같은
  극적인 격차는 드물다. 그래서 20항목에서 멈췄다 — 더 넣어도 노이즈가 늘 뿐이다
- `terms.py` 는 **부분문자열 매칭**(`common in text`)이다. 띄어쓰기 있는 말(`남은 돈`)은
  아예 안 걸리고, 짧은 말(`넘는`, `따름`)은 엉뚱한 질의에 조용히 끼어든다.
  그래서 일상어 길이 3자 이상을 기준으로 삼았다(`과표` 만 손으로 예외 — 주석에 명시)

### 고친 것 6 — `check` 의 백엔드 실패 처리 (세션 4)

검색 품질과는 무관한 수정이다. 지표는 전혀 안 움직인다(R@5 0.900 그대로).

`judge()` 에 `shutil.which("claude")` 가드가 **있었는데도** 이 머신에서 raw 트레이스백이
났다. 이유: `which` 는 성공한다 — PATH 에 파일은 있고 **exec 단계에서** 죽는다
(`OSError: [Errno 8] Exec format error`). 존재 확인과 실행 가능 확인은 다른 문제다.

미처리 실패가 6종이었다. 전부 `JudgeError(RuntimeError)` 로 모았다(`DrfError` 와 같은 관례):

| 실패 | 전에는 | 지금 |
|---|---|---|
| CLI 없음 | RuntimeError | JudgeError |
| **exec 불가 (이 머신)** | **raw OSError** | JudgeError "실행할 수 없습니다" |
| 타임아웃 | raw TimeoutExpired | JudgeError |
| exit != 0 | RuntimeError | JudgeError |
| stdout 이 JSON 이 아님 | raw JSONDecodeError | JudgeError |
| 모델 출력에 JSON 없음 / 판정값 이상 | raw ValueError | JudgeError |

`cli.check` 는 `JudgeError` **만** 잡는다. bare `RuntimeError` 를 잡으면 무관한 오류까지
삼킨다. 출력은 stdout(에러 스트림 아님 — 검색 결과와 이어지는 한 편의 보고서다), **exit 1**:

```
▸ 판단 중 (claude CLI)...
──────────────────────────────────────────────
▸ 판정 건너뜀 — claude CLI 를 실행할 수 없습니다: [Errno 8] Exec format error: 'claude'
  위 검색 결과는 정상입니다. LLM 백엔드를 복구하면 판정까지 나옵니다.
```

**검증 범위를 정확히 알아 둘 것.** 실패 경로 6종은 이 머신에서 실제로 확인했고
(exec 불가는 진짜 증상으로, 나머지는 `subprocess.run` 을 monkeypatch 해서) 테스트가 8개 늘었다.
**성공 경로는 유닛 테스트로만 확인했다** — `claude` CLI 가 깨져 있어 실물 판정은 못 돌렸다.
프롬프트·파싱 로직은 건드리지 않았으므로 CLI 가 복구되면 세션 2 와 같이 동작해야 한다.
→ **세션 5 에 CLI 가 복구된 것을 발견하고 실물로 확인했다. 예상대로 동작한다**(§4 표 5/5).
이제는 거꾸로 **실패 경로 6종을 실물로 못 돌린다** — 유닛 테스트가 계속 지킨다.

### 고친 것 7 — 결정문 수집 경로 (P2, 세션 4) — **코드는 됐고 적재는 회귀로 중단**

**틀린 가설 하나를 실측으로 걷어냈다 (§8 규칙대로 축을 분리해 먼저 쟀다).**
"`token_df` 가 결정문까지 포함해 재집계되면서 질의 자체가 바뀌었다" 고 의심했으나 **아니다.**
그 문항의 토큰 19개를 전체 기준(n=1,181)과 조문만 기준(n=1,127)으로 각각 재보니
**df 10% 임계를 넘나든 토큰이 하나도 없다.** 질의는 바뀌지 않았다.

남는 원인은 **크라우딩**이다. 결정문이 두 축의 후보 풀에 그대로 들어온다:

**키워드 축이 더 크게 오염된다** — 한 문항은 kw 상위 30 중 12개가 결정문이다.
결정문은 길고 법인세 어휘가 빽빽해 bigram 키워드 축에서 강하다.

**이건 버그가 아니라 구조적 충돌이다.** eval 30문항은 **전부 조문을 정답으로 기대**하는데,
조문이 아닌 문서를 코퍼스에 넣으면 정의상 조문의 순위가 내려간다. 코퍼스 커버리지(P2)와
현재 eval 이 재는 것이 서로 다른 목표다.

#### 전량 적재까지 가 보고 확인한 것 (세션 4 후반)

사용자 지시로 전량 적재를 끝내고 다시 쟀다. **결과가 훨씬 나쁘다.**

적재 자체는 깨끗하다 — 임베딩 NULL 0, tsv 빈값 0, 실패는 증선위 3건뿐이고 전부
일시적 네트워크 오류다(파싱 실패 아님). 심판례는 791건 중 **240건이 세목으로 걸러졌다**
(지방소득 97 · 부가 65 · 종합소득 22 · 기타 21 · 증여 9 · 양도 8 · 근로소득 6 · 상속 5 ·
취득 4 · 인지 1 · 상증 1 · 개별소비 1). **통과율 70%** 로, 8건 표본에서 본 50%보다 높았다.

**새로 확인된 사실 둘. 둘 다 다음 판단의 근거다.**

**(1) 증선위 868건은 대부분 축 밖이다.** 고정 시드 표본 8건 중 외부감사 관련은
`의결 제2022-182호`(감사보고서 위탁감리) **1건뿐**이었다. 나머지는 공시의무 위반·정기검사·
증권신고서 미제출·토지신탁 선지급·대량보유 보고·미공개정보 이용으로 **전부 자본시장법
소관**이다. 착수 시 "경계"로 분류하고 넣었는데, 실측하니 넣지 말았어야 했다.
본문에 마스킹(`◆◆◆`·`▣▣▣`·`OOOO`)도 심해 검색 대상으로도 나쁘다.
또 **의결번호가 유일하지 않다** — 같은 번호가 서로 다른 결정문 2건에 붙은 사례가 5건 있고
(`의결 제2021-124 호` 처럼 공백이 섞인 표기도 있다) eval 의 label 정확일치와 충돌한다.

**(2) 결정문에는 지금의 eval 채점 방식을 쓸 수 없다.** eval 은 (법령명, label) **정확일치**로
정답을 찾는데, 심판례 551건은 **같은 쟁점을 반복해서 다룬다.** 문항 후보의 유일성을
텍스트 매칭으로 세 봤다(검색 파이프라인이 아니라 `LIKE`):

| 쟁점어 | 재결요지에 등장 | 본문 전체 |
|---|---|---|
| 비사업용(토지) | **41건** | 69 |
| 고유목적사업 | **23건** | 48 |
| 가지급금 | **22건** | 59 |
| 장애인고용부담금 | **16건** | 21 |
| 적정보수 | 3 | 5 |
| 당연 무효 | **1** | 4 |

`questions.yaml` 절차 2번("정답이 여러 문서에 걸리는 주제는 버린다")을 지키면
**쓸 수 있는 문항이 1~2개밖에 안 남는다.** 조문은 "제25조" 하나가 정답이지만,
결정문은 "이 쟁점을 다룬 결정문 여럿" 중 아무거나가 정답이다. **정답이 집합인 자료에
단일 정답 채점을 붙일 수 없다** — eval 문항을 더 쓰는 게 아니라 채점 방식을 먼저 정해야 한다.

**그래서 eval 확장은 여기서 멈췄다.** 문항을 억지로 쓰면 그건 "정답이 유일해 보이는 것만
고른" 표본이 되고, 그건 §7 고친 것 5 에서 배운 실수(문항에 맞추기)를 평가 쪽에서 반복하는 것이다.

### 고친 것 8 — 아직 안 고쳤다: **키워드 축 순위가 동점 때문에 불안정하다** (세션 4)

**이번 세션에서 가장 중요한 발견이고, P2 보다 중요하다. 다음 세션의 1순위로 올린다.**

결정문 코퍼스를 되돌린 뒤 baseline 이 **정확히 복원되지 않았다.** 데이터는 완전히 같은데
(law 5 / article 714 / chunk 1,127 / term_article 8,600 / token_df 22,472 — 전부 일치)
지표가 다르다:

```
세션 시작   R@5 0.900   R@10 0.933   MRR 0.685
되돌린 뒤   R@5 0.900   R@10 0.967   MRR 0.692
```
움직인 문항 둘: **「계열사」 MISS → 4위**, 「사택」 5위 → 6위.
`VACUUM ANALYZE` + `REINDEX` 를 해도 되돌아오지 않았다.

**원인: `ts_rank_cd` 동점이 대량으로 있는데 kw 축 CTE 에 tie-break 가 없다.**
「계열사」 질의의 동점 분포를 실측했다:

| `ts_rank_cd` | 1.4 | 1.3 | 1.1 | 0.9 | 0.8 | 0.7 | 0.6 | 0.5 | 0.4 | 0.3 | 0.2 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 동점 청크 수 | 1 | 1 | 1 | **5** | 4 | 4 | 4 | **9** | **19** | 23 | 74 |

**고유한 순위는 1~3위뿐이고 4위부터는 전부 동점 그룹 안**이다. pool=30 을 자르는 지점은
0.5~0.4 그룹 한가운데다. `ROW_NUMBER() OVER (ORDER BY ts_rank_cd DESC)` 에 결정적
두 번째 키가 없으니 **동점 안 순서는 실행 계획이 정한다.** 정답 시행령 제90조는 0.9 그룹
(5개) 안에 있어 **4~8위 중 아무 데나** 될 수 있다.

- 실행마다 랜덤하지는 않다 — 물리 상태가 같으면 결과도 같다(같은 상태에서 두 번 재봤다)
- 그러나 **코퍼스에 무슨 작업을 하면 순서가 재배치된다.** 11,668행을 넣었다 지운 것이
  dead tuple 과 통계를 바꿨고 그게 계획을 바꿨다

**이게 왜 심각한가.** 이 프로젝트의 개선 판단은 전부 **"1문항 움직임 / 회귀 0건"** 이었다
(§7 고친 것 3·4·5). 그런데 4위 이하는 동점이라 **1문항 움직임이 신호인지 tie 재배치인지
구분할 수 없다.** 과거 결론이 틀렸다는 뜻은 아니지만, **그 판단들의 정밀도가 주장해 온
것보다 낮다.** 「계열사」가 MISS 였던 것도 "API 가 다리를 안 놓아서"(§10)만이 아니라
**동점 순서 운도 섞여 있었다** — 지금은 사전을 안 고쳤는데도 4위다.

**고치는 방법은 싸고 명확하다: kw·vec CTE 에 결정적 두 번째 키(`c.id`)를 넣는다.**
가중치가 아니라 재현성 장치라 불변식 8 과 무관하다. 다만 **넣는 순간 몇 문항이 움직이므로**
그 전후를 같은 세션에서 재고, 그 이후의 모든 수치는 새 기준선으로 봐야 한다.
**세션 4 에서는 손대지 않았다** — 지표를 움직이는 변경이라 사용자 판단이 필요하다.

→ **세션 5 에서 고쳤다. §7 고친 것 9 로 이어진다.** 위 진단 중 "vec 도 같은 문제"는
**실측으로 반증됐다** — 동점은 kw 축에만 있었다.

### 고친 것 9 — 세 축 CTE 에 결정적 tie-break (세션 5) ★ 세대 B → C 경계

**이 변경 전후로 지표의 성격이 달라진다.** 이전 수치는 재현되지 않고, 이후 수치는 재현된다.

#### 먼저 잰 것 — 동점 분포 (착수 전, 세 축 전부)

eval 30문항 전부에 대해 프로덕션과 같은 질의(`expand_query` → `to_tsquery_or` + df 필터)로
축별 상위 200을 뽑아 1차 키의 동점 그룹을 셌다.

| 축 | 상위 30 중 동점 순위 | 동점그룹이 pool 경계를 걸친 문항 | 최대 동점그룹 | 고유 순위 선두 |
|---|---|---|---|---|
| **kw** (`ts_rank_cd`) | **743/900 (82.6%)** | **25/30** | **111** | 중앙값 3 |
| vec (`embedding <=>`) | **0**/900 | 0/30 | 1 | 200 (전 구간) |
| tm (3키 정렬) | **0**/210 | 0/7 | 1 | — (발화 7/30) |

**§7 고친 것 8 의 "kw·vec 둘 다" 는 틀렸다 — 깨져 있던 건 kw 뿐이다.**
vec 은 30문항 × 200순위 = 6,000순위에 동점이 하나도 없다. 256차원 float 거리가 같아지려면
임베딩이 같아야 하는데, **코퍼스에 중복 임베딩·중복 본문·중복 tsv 가 전부 0건**이다(실측).
tm 의 마지막 키도 같은 벡터 거리라 같은 이유로 유일하다.

**경계를 걸친 25/30 이 특히 중요하다.** 동점 그룹이 pool=30 을 가로지르면 순서만이 아니라
**어느 청크가 후보 풀에 들어오는지 자체가 비결정적**이다.

#### 두 번째 키를 무엇으로 할지 — 측정 전에 확정했다

**`c.id` 오름차순.** 지표를 보고 고르면 그건 노브다. 불변식 8 과 충돌하지 않는 근거 넷:

1. **파라미터가 없다.** 기본키라 조정할 값이 아예 없다 — 튜닝 표면이 0이다
2. **기존 순서를 재배치하지 않는다.** 1차 키가 이미 가르는 쌍에는 개입하지 않는다.
   축 순위는 기존 부분순서의 **세분화(refinement)** 지 변경이 아니다
3. **단조변환 불변.** 1차 키에 순증가 변환을 씌워도 동점은 동점, 비동점은 같은 순서라
   결과가 동일하다 — 불변식 8 이 요구하는 바로 그 테스트다
4. **품질을 겨냥하지 않는다.** `c.id` 는 적재 순서일 뿐 관련성 신호가 아니다.
   `c.id DESC` 나 다른 키가 지표가 더 좋아도 바꾸지 않는다

**세 축 전부에 넣었다.** kw 는 실제 수정이고, vec·tm 은 동점 0건이라 **결과를 바꾸지 않는
공짜 가드**다(아래에서 측정으로 확인). 코퍼스가 넓어져 중복 본문이 생기면(증선위 결정문은
마스킹이 심하다) vec·tm 도 같은 병에 걸리므로, 불변식을 축마다 다르게 두지 않았다.

**창 함수의 `ORDER BY` 와 `LIMIT` 의 `ORDER BY` 를 둘 다 고쳐야 한다.** `ROW_NUMBER` 는
`WHERE` 를 통과한 전체 행에 매겨지고 `LIMIT` 이 그 뒤에 자르므로, 둘이 어긋나면 풀에
살아남은 행의 rank 가 1..pool 이 아니게 된다. 실제로 tm 에서 한쪽만 고쳤다가
`tests/test_hybrid_sql.py::test_window_and_pool_orderings_match` 에 걸렸다.

#### 전후 측정 — 같은 세션, 같은 DB 상태에서 4변형

프로덕션 SQL 을 문자열로 바꿔 끼워 한 번에 쟀다(임베딩은 변형과 무관하므로 재사용).

| 변형 | R@5 | R@10 | MRR |
|---|---|---|---|
| V0 무 (= 세션 4 상태) | 0.900 | 0.967 | **0.692** |
| V1 kw 만 | 0.900 | 0.967 | **0.679** |
| V2 vec+tm 만 | 0.900 | 0.967 | **0.692** |
| **V3 전부 (채택)** | **0.900** | **0.967** | **0.679** |

- **V0 이 STATE 기준선을 정확히 재현했다** — 이 측정 하네스를 믿을 근거다
- **V2 는 V0 과 문항별 순위까지 완전히 같다** — vec·tm 키가 no-op 이라는 게 주장이 아니라 측정이다
- **V1 == V3** — 움직임은 전부 kw 에서 나온다

**움직인 문항 3개가 전부다.**

| 문항 | 전 | 후 |
|---|---|---|
| 법인세 과세표준은 언제까지 신고해야 하나요 | 10위 | **8위** |
| 자산을 다시 평가해서 장부상 이익이 늘었는데 | 4위 | **3위** |
| 감사인이 자료를 내놓으라고 하면 회사는 따라야 하나요 | 1위 | **2위** |

**MRR 이 0.692 → 0.679 로 내려갔다. 그래도 키를 바꾸지 않았다.**
`c.id` 는 측정 전에 확정한 것이고, 지표가 오르는 두 번째 키를 찾아 나서는 순간 그건 노브다.
그리고 **0.692 는 애초에 품질 측정값이 아니었다** — 같은 데이터가 0.685 도 냈다(§7 고친 것 8).
내려간 게 아니라, 추첨 결과 하나가 재현 가능한 수치로 바뀐 것이다.
R@5·R@10 은 둘 다 그대로다.

#### 재현성 검증 4가지

1. **같은 DB 상태에서 `cli eval` 두 번** → 문항별 순위까지 완전히 일치 (성공 기준 3)
2. **코퍼스 교란 → 되돌림** (성공 기준 4): 청크를 3배(1,127 → 4,508)로 복제했다 지우고
   VACUUM 없이 재측정. 코퍼스는 md5 까지 복구됐고 **V0·V3 둘 다 지표가 복귀했다.**
   즉 **이 교란은 세션 4 의 재배치를 재현하지 못했다** — 원본 행의 힙 위치가 안 움직인다
3. **계획 노브 6가지**(seqscan/bitmapscan/indexscan 끔, work_mem 64kB, 병렬 4) →
   V0·V3 둘 다 안 움직였다. 이 코퍼스 크기에서는 V0 도 우연히 안정적이다
4. **물리적 행 순서만 바꿔서 교차 측정** ← **결함과 수정을 직접 증명한 것은 이것이다**

2·3 이 재현에 실패했으므로 메커니즘을 직접 찔렀다. GIN 경로는 Bitmap Heap Scan 이 행을
**힙 순서로** 돌려주고 Postgres 의 quicksort 는 **안정 정렬이 아니다** — 그래서 동점 안
순서는 정렬 입력의 물리적 순서에 좌우된다. 같은 1,127행을 물리 순서만 바꿔 임시 테이블
둘(`ORDER BY id DESC`, `ORDER BY md5(id::text)`)에 담고 kw 축 상위 30을 비교했다:

| | 물리 순서를 바꿨을 때 kw 상위 30이 달라진 문항 |
|---|---|
| V0 (tie-break 없음) | **30 / 30** |
| V3 (tie-break 있음) | **0 / 30** |

V0 은 상위 30자리 중 **19~27자리**가 어긋나고 **풀에 드는 청크 집합 자체가 최대 9건** 다르다.
데이터는 완전히 같다(id 차집합 0건). **코퍼스에 무슨 작업을 하든 이 순서는 바뀔 수 있다.**

#### 정직하게 적어 둘 것 셋

- **세션 4 재배치의 정확한 방아쇠는 규명하지 못했다.** 복제 교란도 계획 노브도 재현하지
  못했고, 진짜로 재현하려면 결정문 11,668청크를 다시 넣었다 지워야 한다(약 25분).
  **위 4번이 "물리 순서가 바뀌면 30/30 이 흔들린다"를 증명했으므로 더 파지 않았다** —
  방아쇠가 무엇이든 결과는 같고, 고친 뒤에는 방아쇠가 무의미해진다
- **`vec` 축이 HNSW 인덱스를 계속 타는지 확인했다.** `ORDER BY embedding <=> qv, id` 는
  `chunk_embedding_idx` 인덱스 스캔 위에 Incremental Sort 를 얹는다(EXPLAIN 으로 확인).
  seq scan 으로 떨어졌다면 근사 검색이 정확 검색으로 바뀌어 "no-op" 주장이 깨졌을 것이다
- **과거 결론들이 틀렸다는 뜻은 아니다.** §7 고친 것 3·4·5 는 전부 세대 A·B 의
  "1문항 움직임 / 회귀 0건" 이었고, 그 1문항이 신호인지 tie 재배치인지 이제 와서 가릴 수
  없다. **다시 재려면 세대 C 에서 다시 재야 한다.** 지금 다시 재지는 않았다

### 고친 것 10 — eval 30 → 50문항 (세션 6) ★ 세대 C → D 경계

#### 1. 기존 30문항은 회귀 0건 — 순위까지 비트 단위로 같다

몇 개 움직였는데 이게 신호인지 tie 재배치인지 모르겠다" 가 됐을 것이다. 지금은 단언할 수 있다.

#### 2. 신규 문항이 기존의 **절반** 성능이다 — 지표가 문항 선정에 기대고 있었다

R@5 0.900 vs **0.450**. 문항은 고치지 않았다(`questions.yaml` 절차 4).
**기존 30문항이 중립적인 표본보다 쉬웠다는 뜻이다.** 이 프로젝트가 내세워 온 0.900 은
검색 성능만이 아니라 문항 선정도 함께 반영하고 있었다. 늘리지 않았으면 못 봤다.

왜 그런가에 대한 가장 그럴듯한 설명(확증은 아니다): **절차 2가 중심 조문을 계통적으로
걸러낸다.** 본법·하위법령에 걸친 주제를 버리면, 법인세법처럼 법-령-규칙이 촘촘히 짝지어진
코퍼스에서는 **주변부 조문만 남는다.** 표본 481개 중 244개(51%)가 이 규칙으로 탈락했다.
기존 30문항의 중심 주제들(법인세율·과세표준 신고·접대비)은 이 규칙을 지금 적용하면

### 고친 것 11 — 과거 개선 4가지를 세대 D 에서 다시 쟀다 (세션 7) ★ 재측정, 코드 변경 0줄

**§7 고친 것 1·2·3·4 는 전부 세대 A(15문항)·B(30문항)에서 "1문항 움직임 / 회귀 0건"으로
채택됐고, 세대 B 판단은 tie 재배치와 구분되지 않았다**(§7 고친 것 9). 세대 D 는 재현되는
50문항이므로 **어느 것이 진짜 이득인지 처음으로 잴 수 있다.** 각각을 하나씩 껐다(leave-one-out).

**프로덕션 코드는 한 줄도 안 고쳤다.** 셋은 인자로 끄고, 축3 tie-break 만 `db._HYBRID_SQL` 을
문자열로 가져와 정렬 키를 지운 변형을 만들었다(세션 5 의 `variants.py` 패턴).

#### 하네스를 믿을 근거 (측정 결과보다 이걸 먼저 봐라)

- **전부 켠 변형(`ALL`)이 프로덕션 `cli eval` 과 문항별 순위까지 완전히 일치**한다
  (0.720 / 0.780 / 0.547). 세션 5 의 V0 검증과 같은 장치다
- **5변형 × 2회 실행에서 문항별 순위가 전부 일치**한다 (성공 기준 3)
- 임베딩은 질의문마다 캐시했다 — 사전확장을 끄면 질의문이 달라지므로 **벡터도 같이** 바뀐다.
  이건 프로덕션과 같은 동작이다(`cli._search` 가 확장문을 임베딩한다)

#### 끄는 방법 — 각각이 프로덕션의 어느 장치인가

| 장치 | 끄는 법 | 켠 상태에서 무엇을 하나 |
|---|---|---|
| 문서빈도 필터 | `to_tsquery_or` 에 `df` 를 안 넘긴다 | df>10% bigram 제거 (`MAX_DF_RATIO`) |
| 용어 사전 질의 확장 | `expand_query` 를 안 부른다 | 일상어→법령용어를 질의문에 덧붙임 |
| 축3 (용어연계) | `link_terms=[]` | `term_article` 조문을 3번째 RRF 리스트로 |
| 축3 등장횟수 tie-break | tm 정렬에서 `max(등장횟수) DESC` 제거 | 핵심용어 조문끼리의 순서를 가름 |

> **사전확장 off 는 `link_terms` 를 건드리지 않는다** — 축3 은 그대로 발화한다.
> 둘을 분리해서 재기 위한 것이고, 실제로 분리된다(아래 #3 과 #27 을 보면 알 수 있다).
> 축3 tie-break 는 창 함수와 `LIMIT` 양쪽 `ORDER BY` 에서 같이 뺐다(불변식 9).

#### 1. 문서빈도 필터가 압도적이고, **유일하게 신규 20문항에 듣는다**

23문항이 움직이고 그중 19개가 악화다. 신규 20문항에서 R@5 0.450 → **0.250**.

**세대 D 에서 그 판단이 가장 강하게 확인됐다.** 넓은 평탄역(0.5~0.1)까지 이미 확인돼 있으니

끄면 **좋아지는 문항도 4개** 있다(#2 8→7, #9 4→2, #28 2→1, #40 MISS→10). 필터가 만능은

- **#3 은 사전확장에만, #27 은 축3 에만 걸린다.** 두 장치가 서로 대체 불가능하다는 증거다
  (#3 접대비는 코퍼스에 0청크라 질의문을 안 바꾸면 못 찾는다 — §7 고친 것 2)
- **축3 등장횟수 TB 가 움직이는 문항은 세대 A·B 와 똑같이 #9 하나뿐이다.**
  15 → 30 → 50문항으로 세 번 늘렸는데 이 tie-break 가 갈라 주는 문항이 계속 하나다.
  §7 고친 것 4 의 "안전하다는 것이지 효과가 크다는 게 아니다" 가 세대 D 에서 재확인됐다

#### 3. "회귀 0건" 은 세대 D 에서 성립하지 않는다 — #10 이 회귀다

**#10(자산 재평가, 법인세법 제18조)은 사전확장과 축3 을 켜면 2위 → 3위로 내려간다.**
§7 고친 것 2·3 은 "회귀 0건" 으로 채택됐는데, 세대 D 에서는 각각 회귀 1건을 달고 있다.

**과거 측정이 틀렸다는 뜻은 아니다.** #10 은 세션 3 에 30문항으로 늘리며 들어온 문항이고,
그때 사전확장·축3 은 **이미 켜져 있었다** — 즉 이 문항에 대해 껐다 켜서 재본 적이 자체가 없다.
세대 A(15문항)에는 이 문항이 없었다. **안 보였던 게 아니라 잰 적이 없었던 것이다.**

순이득은 여전히 양수다(사전확장 개선 2 / 회귀 1, 축3 개선 2 / 회귀 1). 다만
**이 프로젝트가 "회귀 0건" 을 채택 근거로 써 온 관행은 이제 조건을 붙여야 한다** —
"그 시점 문항 집합에서 회귀 0건" 이다. §8 항목 8 에 남겼다.

#### 정직하게 적어 둘 것 셋

- **넷 다 켜 둔 채로 끝냈다.** 이득이 작다고 걷어내지 않았다 — 걷어내는 것도 변경이고
  표본은 여전히 50이다(세션 7 착수 지시). **판단은 사용자 몫이고 아직 안 물었다**
- **조합은 재지 않았다.** 2⁴ 를 훑어 지표가 오르는 조합을 찾는 건 노브 탐색이지
  재측정이 아니다. leave-one-out 만 했다
- **하네스는 레포에 안 넣었다** (세션 5 `variants.py` 와 같다). 위 「끄는 방법」 표만 있으면

## 8. 틀렸던 진단 (같은 실수를 반복하지 말 것)

1. **"시행령이 본법을 밀어낸 라벨 문제"** → 틀렸다. 상위에 온 건 무관한 조문이었다.
2. **"model2vec 정적 임베딩의 한계"** → 틀렸다. 축별로 재보니 **벡터가 키워드보다 나았고**
   (pool 30 밖: 벡터 3건 vs 키워드 6건), **하이브리드가 벡터 단독보다 더 나빴다**(0.533 vs 0.667).
   문제는 임베딩이 아니라 키워드 축이었다.
3. **"결정문 적재가 `token_df` 를 바꿔 질의가 달라졌다"** (세션 4) → 틀렸다. 해당 문항의
   토큰 19개를 전체/조문만 두 기준으로 재보니 **df 10% 임계를 넘나든 토큰이 0개**였다.
4. **"되돌린 뒤 지표가 다른 건 HNSW 가 근사 인덱스라서다"** (세션 4) → 틀렸다.
   `VACUUM ANALYZE` + `REINDEX` 를 해도 그대로였다. 결과는 결정적이었다.
   진짜 원인은 **키워드 축의 동점**이었다(§7 고친 것 8).
5. **"vec 축에도 같은 동점 문제가 있다"** (세션 4 의 §7 고친 것 8) → 틀렸다.
   실측하니 vec 은 30문항 × 200순위에 동점 **0건**, tm 도 0건이고 **kw 만 743/900** 이었다.
   중복 임베딩·본문·tsv 가 코퍼스에 0건이라 구조적으로 동점이 안 생긴다(§7 고친 것 9).
6. **"코퍼스를 건드렸다 되돌리면 순위가 재배치된다"** (세션 5) → **이 형태로는 재현 안 됐다.**
   청크를 3배로 복제했다 지워도, 계획 노브를 6가지로 흔들어도 V0 이 그대로였다.
   원본 행의 힙 위치가 안 움직이기 때문이다. 진짜 변수는 "코퍼스를 건드리는 것" 자체가
   아니라 **정렬 입력의 물리적 행 순서**였고, 그건 물리 순서만 바꿔 재서 확인했다
   (V0 30/30 흔들림 vs V3 0/30). **원인을 코퍼스 조작에서 찾다가 한 겹 놓칠 뻔했다.**
7. **"신규 문항이 어려운 건 하위법령 비중이 올라가서다"** (세션 6) → 틀렸다.
   하위법령이 17% → 50% 로 는 건 맞지만 **본법 문항도 0.92 → 0.50 으로 똑같이 반토막**이다.
   자료 종류가 아니라 **주제의 중심성** 문제였다(§7 고친 것 10).
   그럴듯한 설명이 먼저 떠올랐지만 축을 분리해 재고 나서야 기각됐다.
8. **"사전확장·축3 은 회귀 0건이다"** (세대 A·B 채택 근거) → **세대 D 에서는 아니다.**
   둘 다 #10(자산 재평가)을 2위 → 3위로 내린다(§7 고친 것 11). 과거 측정이 틀린 게 아니라
   **그 문항이 들어왔을 때 이 장치들은 이미 켜져 있어서 껐다 켜서 잰 적이 없었다.**
   **"회귀 0건" 은 문항 집합에 상대적인 주장이다** — 앞으로는 "어느 세대에서" 를 붙여 적어라.

**교훈: 지표가 나쁠 때 축을 분리해 따로 재보기 전에는 원인을 말하지 마라.**
Step 0 의 임베딩 프로브가 10건짜리 코퍼스라 6/6 Top-1 이 나온 것도 같은 함정이었다 —
1,127청크에서는 전혀 다른 그림이었다.

축별 순위를 재는 스크립트 패턴(재사용 가치 있음): 벡터는 `ORDER BY embedding <=> qv`,
키워드는 `ORDER BY ts_rank_cd(tsv, q) DESC` 로 각각 `ROW_NUMBER()` 를 매기고
정답 조문의 순위를 뽑아 비교한다.

## 11. 함정 (모르면 시간 낭비함)

- **전역 TDD 훅이 켜져 있다.** `~/.claude/hooks/tdd-autotest.py` 가 `pyproject.toml` 을 보고
  Write/Edit 마다 pytest 를 돌리고 **실패하면 다음 작업을 막는다.** 방해가 아니라 안전망이니
  끄지 말고 테스트를 먼저 써라. 탈출구는 `CLAUDE_TDD_HOOK=0` 또는 `.no-tdd` 파일이지만 쓰지 마라.
  `~/.claude/hooks/tdd-guard.py` 는 테스트 비활성화/삭제만 막는다.
- **`embed_one()` 은 numpy 배열을 반환해야 한다.** 파이썬 list 로 넘기면 psycopg 가
  `double precision[]` 로 어댑트해서 pgvector 의 `<=>` 가 안 걸린다. 실제로 여기서 한 번 깨졌다.
- **eval 의 법령명은 정확일치로 비교한다.** 부분일치로 하면 `법인세법` 이 `법인세법 시행령` 에도
  걸려서, 양쪽에 다 있는 제6조가 오탐이 된다.
- **`ingest --query` 는 정확일치 법령만 적재한다.** 검색이 부분일치라 '법인세법'으로
  시행령까지 딸려오기 때문.
- **`refresh-terms` 는 서버가 매달리면 몇십 분씩 안 끝난다.** 실제로 겪었다: HTTPS 연결은
  ESTABLISHED 인데 데이터가 안 오고 CPU 0%. requests 의 `timeout` 은 **읽기 사이 간격**이라
  서버가 찔끔찔끔 보내면 안 걸린다. 용어마다 즉시 커밋되고 **이미 받은 용어는 건너뛰므로,
  끊기면 그냥 다시 돌려라**(`--force` 를 줘야 전부 다시 받는다). 큰 응답 4개(벌칙·벌금·
  징역·사업연도, 각 2~3MB)가 문제다.
- **`lstrmRltJo` 는 응답이 커서 기본 30초 타임아웃으로는 실패한다.** `fetch_term_articles()`
  가 180초를 쓴다. 다른 target 을 붙일 때도 응답 크기를 먼저 재 볼 것.
- **`term_article` 데이터는 DB 에만 있다.** 세션 2 에서 쓴 응답 XML 캐시는 세션 임시 디렉터리라
  이미 사라졌다. 이 테이블을 비우면 **다시 네트워크로 받는 수밖에 없다** — 함부로
  `TRUNCATE` 하지 마라. 백업이 필요하면 `pg_dump -t term_article`.
- **Bash 툴의 `grep` 은 셸 함수로 가려져 있다** (`~/.claude/shell-snapshots/…` 가 정의).
  실제로 매치가 있는데 **조용히 0건을 반환**했다. `git grep` 도 같은 증상이 났다.
  비밀값 스캔처럼 "0건" 이 곧 결론이 되는 검사는 **`/usr/bin/grep` 절대경로**를 써라.
  일반 코드 탐색은 Grep 툴을 쓰면 된다.
- **`lstrmRlt` 응답을 `root.iter('연계용어')` 로 훑으면 동음이의어가 뒤섞인다.**

## 12. 컨텍스트 관리

`.claude/settings.local.json` 에 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=50` 이 들어 있다.
**훅으로 자동 compact 는 불가능하다** — 컨텍스트 사용량을 받는 훅 이벤트가 없고
compact 를 시키는 출력 필드도 없다. 이 env 는 **세션 시작 시** 읽히므로 다음 세션부터 적용된다.
이 파일만 지우면 원복된다.

운영 방식: **알아낸 것은 즉시 이 문서에 적고, 작업 경계에서 `/clear`.**
컨텍스트를 지식 저장소로 쓰지 마라 — 요약은 숫자와 고유명사를 가장 먼저 버린다.
긴 XML·psql 덤프는 서브에이전트에 격리한다.

세션 4 에서 실제로 겪은 것 둘:
- **`grep` 함정을 또 밟았다.** 이 셸에서 `grep` 은 `claude` 로 가려져 있어 파이프에 쓰면
  엉뚱한 출력이 나온다. §11 첫 항목대로 **`/usr/bin/grep` 절대경로**를 써라.
- **서브에이전트가 내용 없이 idle 로 빠지는 일이 두 번 있었다.** 두 번째부터는 기다리지 말고
  응답 구조 조사는 **직접 하되 태그 이름만 출력하는 스크립트**를 써라 — 그게 원문을
  컨텍스트에 들이지 않으면서 더 빠르다. 세션 4 의 `probe_struct.py` 패턴이 그것이다.
